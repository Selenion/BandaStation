# Хранение атмоса: память и проверка поведения

Этап после [EXCHANGE_OPTIMIZATION.md](EXCHANGE_OPTIMIZATION.md), ABI 11.
Формулы, порядок обработки газов, группы, таймеры и протокол DM не меняются.
Последующий аудит всего процесса нашёл удержание FFI-пакетов в DM-обёртке;
причина, исправление и новые замеры: [PACKET_MEMORY.md](PACKET_MEMORY.md).

## Главный подтверждённый расход

В [предыдущей переписи](COST_AUDIT.md) Rust удерживал около 458–461 MiB
живых запрошенных аллокаций. Два набора BTreeMap с 780300 Cell и Tile
требовали 372.37 MiB только под узлы таблиц. Около 87% записей — космос.
Газовые массивы обоих состояний занимали около 17 MiB; результаты реакций —
менее 0.1 MiB. Удаление массивов результатов не решает основную проблему.

Это не полная память DreamDaemon. В старой диагностике оставалось ещё около
338 MiB дополнительных выделений BYOND/других библиотек и накладных расходов,
не объяснённых живыми Rust-аллокациями. Их источник не установлен.
Private memory включает также удерживаемые страницы аллокатора; её нельзя
складывать с working set или считать точным размером живых структур.

## Изменение

`storage.rs` хранит записи по ID в блоках по 8. Внутри блока нет отдельных
ключей и узлов дерева. Неизменённые блоки разделяются между снимками через Arc;
первая изменяющая операция копирует только свой блок. При синхронизации рабочее
состояние снова разделяет актуальные блоки опубликованного состояния. Холодные
записи не накапливают вторую копию после прошлой активности.

Сохраняются два логических состояния и неизменность удержанных снимков.
Порядок обхода остаётся возрастающим по ID, включая ID 0 и пропуски.
Газовые массивы, ключи, Some(0), отрицательный ноль и порядок суммирования
копируются без преобразований. Получение двух изменяемых записей делит
массив безопасными срезами; ссылок на разные записи одного блока это не смешивает.

Изменение общего `last_share` космоса больше не записывает 679448 Tile.
Публикация читает скаляр своего снимка Schedule. Новая или заменённая смесь
сохраняет локальное значение до следующего расчёта, как до оптимизации.
Обычный обмен продолжает использовать прежние локальные рабочие поля.
Замена/удаление пола сначала ищет связанные записи через неизменяемый обход,
затем изменяет только найденные: просмотр карты не копирует все блоки.
Стартовая пересборка BTreeMap больше не нужна.

## Сравнение с Paradise

Проверен Paradise `5aca8afbcf00ef1f2bb96e179bf1389289551689`:
[модель](https://github.com/ParadiseSS13/Paradise/blob/5aca8afbcf00ef1f2bb96e179bf1389289551689/rust/src/milla/model.rs),
[переход между состояниями](https://github.com/ParadiseSS13/Paradise/blob/5aca8afbcf00ef1f2bb96e179bf1389289551689/rust/src/milla/tick.rs#L95).
MILLA использует плотные массивы на z-уровень, два буфера и копирование
предыдущего буфера целиком, в том числе для замороженного уровня.
Мы используем плотное хранение внутри блоков, но разделяем холодные блоки:
это позволяет сохранить более крупное состояние Banda без двух полных копий.
Это собственная оптимизация хранения, а не утверждение, что Paradise использует COW.

У Paradise восемь газов и другой алгоритм обмена. Пересчёт размеров его Tile
не является замером работающего Paradise и не доказывает экономию сервера.

## Воспроизводимый микрозамер

`cargo run --manifest-path rust/atmos/Cargo.toml --example storage --target i686-pc-windows-msvc --features byond --release`

`--features byond` сохраняет экспорт API в собираемой рядом DLL.
Пример считает запрошенные живые байты через System allocator, без DM
и непустых динамических газовых массивов. 780300 Cell/Tile, i686:

| Представление | MiB |
| --- | ---: |
| BTreeMap, одно состояние до упаковки | 342.52 |
| BTreeMap, одно состояние после упаковки | 186.45 |
| BTreeMap, пик пересборки одного состояния | 414.42 |
| BTreeMap, два упакованных состояния | 372.91 |
| Блоки по 8, одно состояние | 181.09 |
| Блоки по 8, два полностью общих состояния | 181.83 |
| Блоки по 8, изменены 12.5% соседних ячеек | 204.34 |
| Блоки по 8, изменена вся карта | 361.92 |

Здесь использованы настоящие Cell/Tile с их выравниванием; прежняя модель
узлов по размеру payload давала 372.37 MiB вместо 372.91 MiB.
Цена начального клонирования таблиц блоков в окончательном запуске — 4.01 ms;
изменение первых 12.5% — 22.8 ms. Это не время игрового тика. Последующие синхронизации
переносят ссылки только на затронутые блоки. Изменение одной записи может
скопировать до 7 соседних записей и их динамические данные. Рассеянная
активность уменьшает экономию, удержанные внешние снимки продлевают жизнь блоков.
Размеры Option<Cell>/Option<Tile> проверены: 80/160 B на целевой архитектуре.

Первый прототип с блоками по 128 экономил ещё около 3 MiB на холодной карте,
но копировал больше соседних смесей. Отдельный фиксированный сценарий:
780300 записей, первые 100000 содержат кислород/азот и газовый архив;
120 синхронизаций с записями в ID `1 + n*997 % 100000`.

| Размер блока | 32 записи/тик: время, ms | 512 записей/тик: время, ms | 512 записей/тик: живые MiB |
| --- | ---: | ---: | ---: |
| 8 | 14.1 | 310.7 | 200.25 |
| 16 | 22.4 | 645.4 | 200.26 |
| 64 | 88.6 | 2014.1 | 208.81 |
| 128 | 200.4 | 3540.5 | 218.98 |

Это время всех 120 синхронизаций и записей в изолированном Rust-примере,
без игрового расчёта. Выбран блок 8. Сценарии 32/512 записей включены в
`examples/storage.rs`; размер меняется одной константой `PAGE_SIZE`, без
настроек игрового сервера. Первичная серия и исходники вариантов сохранены
в `tmp/atmos-memory-page-bench`, окончательная серия — в результатах этого этапа.
Повторный запуск сохранённого примера дал 16.2/384.2 ms для 32/512 записей;
это отдельный запуск с уже использованным аллокатором, не статистическая серия.

## Проверки

72 Rust-теста, fmt, clippy. Новые проверки охватывают порядок, пустые позиции,
замену и удаление, ID 0, неизменность снимков при парной записи в один/разные
блоки, совместное хранение холодного блока и повторную синхронизацию с
добавлением/удалением. Прежний тест замены смеси космоса дополнен удержанными
снимками до и после замены.

Дополнительный маленький тест входящих пакетов: 100000 чтений list(0) через
native 24. Win32 HeapSummary allocated вырос на 672 B против 512 B в контрольном
DM, committed — на 4096 B в обоих. Это проверка неизменённого пути ReadList
в старой диагностической DLL ABI 9, не аудит всех видов списков и ссылок.
Накопление сотен MiB этим сценарием не воспроизведено.

`integration-memory-04`: 12 мировых сценариев, 49 графов по 20 тиков,
11 проверок очередей/жизненного цикла, наследование пола, 16 привязок,
7 отложенной инициализации, 32 API, парный контакт с огнём, 21 панель/ошибки,
20 обмена и ленивых эффектов, 6 helper-сравнений. Расхождений и runtime нет.

Прототип с блоками 128, `world-memory-02`: полная MetaStation, 780300 ячеек, 16/16 функциональных
проверок. Строгий фильтр world_adapter отклонил прогон из-за известного
исходного DM-runtime при удалении рыбьего хвоста во время инициализации.
`functional-diagnostic.json` сохраняет этот статус; чистой проверкой мира
этот прогон не считается. Несвязанная ошибка не исправлялась.

## Полная карта: живое хранение

Отдельная инструментированная копия `audit-rust-memory-idle-01` считает
запрошенные живыми Rust-аллокациями байты и уникальные Arc-блоки.
Счётчик снимается до выделений самой переписи. Эта копия не используется
для чистого сравнения CPU, в manifest стоит `diagnostic_instrumentation`.
Рабочая DLL не содержит аллокатора/экспорта аудита.

После окна на MetaStation, 780300 ячеек, 679448 Space в каждом состоянии:

| Данные | Ранее | Сейчас |
| --- | ---: | ---: |
| Живые запрошенные Rust-аллокации | 460.78 MiB | 247.93 MiB |
| Хранение Cell/Tile с таблицами и заголовками | 372.91 MiB | 181.86 MiB |

Первая строка сравнивает предыдущий аудит ABI 9 с текущим ABI 11, а не две
DLL в одном запуске. Размеры Cell/Tile, число ячеек и Space совпадают; прежняя
организация хранения не менялась на этапе сокращения обмена ABI 10/11.
Вторая строка использует измеренную модель упакованных BTreeMap на настоящих
типах и перепись реально уникальных блоков текущего мира.
Экономия живых Rust-данных — около 212.85 MiB, или 46.2%.

Во втором состоянии дополнительно выделены 12 блоков Cell и 19 блоков Tile;
остальные разделяются с первым. Помимо хранения записей остаётся около 66 MiB
на индексы, версии, непустые газовые массивы, очереди и другие данные backend.
За минуту live не рос: 247.96 → 247.93 MiB. Это не проверка полного раунда.

Проверка отдельного DM-списка на 65025 тайлах: HeapSummary allocated относительно
начала +3.10 MiB после наполнения, +0.62 MiB после Cut; замена очищенного списка
на новый освобождает ещё 1467 B. Большое удержание ёмкости этим сценарием не
подтверждено; адаптер для этой гипотезы не изменялся. Полные попытки через
обход `world` не уложились в таймаут и результата не дали.

## Память и CPU всего процесса

Windows i686, BYOND 516.1688, rust-g 6.2.0, MetaStation 255×255×12,
seed 29051994, 30 игровых секунд прогрева, 60 секунд измерения, без клиентов.
Итоговая DLL: `553671f5656e8462a20df22a2356a281613bf6dcbc633a93e1b76cba2a9dda12`.
Во всех чистых итоговых захватах и СМ использован прежний DMB
`6703ae967c2cd4492191257b6cc136518a56751a2e6c7bfbe005e047f6632b30`;
DM-код не менялся. Полные метрики: [MEMORY_RESULTS.json](MEMORY_RESULTS.json).

| Сценарий | Private peak до / после, MiB | CPU до / после, % одного ядра | Проходов SSair до / после | Реальное окно до / после, s |
| --- | ---: | ---: | ---: | ---: |
| Покой | 2817.1 / 2551.7 | 18.66 / 16.40 | 120 / 120 | 60.08 / 60.14 |
| Поджог | 2573.9 / 2261.6 | 30.97 / 28.09 | 105 / 107 | 66.93 / 66.20 |
| СМ, диагностика | 2511.4 / 2285.1 | 38.81 / 39.04 | 101 / 98 | 68.98 / 71.16 |

Для покоя заново выполнен контроль с прежней DLL BTreeMap
`compare-rust-memory-control-idle-01`. Старый исторический покой давал 13.54% CPU;
новый контроль — 18.66%, поэтому сравнение только с прежним числом создавало
ложное впечатление большой CPU-регрессии. Стартовое число pipenet различается:
296 в историческом покое, 331 в контроле, 296 в окончательном новом захвате.
В поджоге тоже различаются стартовые нагрузки: 343/296 pipenet и 119/89 active turf.
Это единичные захваты, а не доказательство точного процента выигрыша CPU.

Диапазоны private в покое перекрываются: 2529.4–2817.1 до и 2535.5–2551.7 MiB
после. Снижение пика на 265 MiB нельзя целиком приписать COW; перепись живых
Rust-данных выше подтверждает эффект хранения независимо от private процесса.
Для огня наблюдалось снижение пика на 312 MiB, но полного контроля фоновых
объектов/RNG и удержания памяти аллокатора тоже нет.

СМ сохранил те же исходные ошибки `null.z` и `removeStaticPower` голодека.
Все входы инцидента совпадают с прежним захватом; настоящая СМ удалена взрывом,
радиус 35. Это диагностические CPU/RAM и число проходов, не чистая парная проверка.
`compare-rust-memory-fire-01` исключён: его начало пересеклось с отдельной
диагностикой списка. Прогоны с блоками 128 остаются историей прототипа.

До последующего исправления удержания пакетов память процесса оставалась выше исходного DM
(около 1669 MiB в покое, 1697 MiB в огне). Включать backend по умолчанию
эти данные не обосновывают. Linux, полный раунд и нагрузка с 50+ игроками не проверены.
