# Прямая публикация и контрольные снимки

Газ остаётся в Rust. Для уже выданных DM-смесей основной поток записывает
числа и списки через BYOND 516 C API. DM сохраняет объекты смесей, ссылки
на живой `moles`, конструкторы, игровые обработчики и жизненный цикл атомов.
Контрольный снимок для обнаружения прямых правок списка хранится в Rust:
три скаляра и упорядоченные пары ключ/значение трёх списков. Полного второго
DM-зеркала карты этот механизм не создаёт.

## Порядок и владение

- Пакет ограничен 256 строками. Его формирует тот же код, что прежнюю
  публикацию 73. Формулы, последовательность строк и точность не меняются.
- Снимок мира освобождается до возврата в DM. Курсор удерживает числовые
  строки и контрольные снимки выданных смесей, без `Arc<Frame>`: callback
  не должен вызывать копирование всего мира при следующей записи.
- Rust применяет числовую часть строки, затем останавливается перед
  изменением оверлея/очага. DM исполняет обработчик этого тайла до применения
  следующей строки. Упреждающая запись всех строк нарушила бы порядок.
- Перед записью проверяются координаты, версия и незавершённая замена пола.
  Удалённые привязки не получают старое состояние.
- Живой список `moles` сохраняет идентичность; архив и результаты заменяются
  новыми списками. Уже выданный readonly-объект обновляется на месте.
- Служебная строка повторно проверяет кэш после предыдущих callbacks.
  Если смесь изменилась напрямую, прежний DM-путь читает свежую полную смесь.
  Тепловая строка удерживает baseline момента формирования пакета.
- Пространство, создание смеси и редкие несовместимые с быстрым путём
  состояния используют существующий декодер. Это не заменяет игровой
  результат приближённым значением.
- Если изменились только параметры очага, возвращаются четыре числа очага
  и первые 12 служебных полей. Повторного газового пакета, разбора молей
  и второй проверки оверлея в DM нет. Для изменившегося оверлея сохраняется
  исходный выбор между `update_visuals(moles)` и `apply_gas_overlays`.
- После ошибки незавершённый курсор освобождается, затронутые кэши считаются
  устаревшими. Пакет игровых эффектов и правила его фиксации не меняются.

Ссылки BYOND контрольных снимков принадлежат отдельному реестру основного
потока; worker их не получает. Замена привязки освобождает снимок, закрытие
владельца освобождает все его снимки и незавершённые пакеты. `DecRef` выполняется
после освобождения mutex, поскольку освобождение ссылки может вызвать DM.

## Native операции

Все операции вызываются синхронно из основного потока, после числового
идентификатора владельца. Старый интерфейс пакетов сохранён.

| Код | Аргументы после владельца | Результат |
| --- | --- | --- |
| 74 | — | Проверка доступности C API и имён полей |
| 75 | Плоские тройки `cell_id, cache_mode, service` | Дескриптор пакета |
| 76 | Дескриптор, phase, context, output | 1 завершён; 2 создать binding; 3 оверлей; 4 прежний декодер; 5 параметры очага |
| 77 | Дескриптор | Освобождение, включая повторный вызов |
| 78 | Cell ID, mixture | Запомнить контрольный снимок |
| 79 | Cell ID, mixture | 2 совпадает; 1 различается |
| 80 | Cell ID | Освободить контрольный снимок |
| 81 | Cell ID, output | Экспорт шести полей только для прежнего пути |

`context` содержит positions, типы газов, типы реакций, таблицу оверлеев,
SSmapping и INITIALIZED_1. У него нет постоянного native-владельца.
Оверлеи сравниваются по настоящим image-ссылкам с текущим смещением плоскости.
Повторное неизменившееся представление не возвращается в DM. Газ не читается
в DM ради такой проверки.

## Проверка

`tools/atmos/phase_world.py` проверяет сценарии против сохранённого исходного
DM, порядок callback между строками, мутацию сохранённой ссылки, независимость
baseline, порядок ключей, нулевой/отсутствующий результат, пропущенную
публикацию и прежние проверки пола/очагов/оборудования. Отдельная проверка
утверждает, что использован native-путь: одного совпадения с fallback мало.
Ошибка внутри обработчика оверлея проверяется на обоих путях: уже выполненные
эффекты остаются, недоставленный кэш становится устаревшим и восстанавливается
чтением Rust; незавершённый native-курсор освобождается.

Проверка `direct-publication-05` на BYOND 516.1688: 12 сценариев мира,
49 графов / 980 шагов, 72 проверки обмена, проверки оборудования, замены пола
и worker — без сбоев. Все 107 Rust-тестов, Clippy с `-D warnings` и rustfmt
прошли. Компактное событие очага отдельно проверено по полям, отсутствие
очага — по обнулённому хвосту; игровой тест подтверждает использование этого
пути при обработке ожидающего очага. Исходные артефакты находятся в
`tmp/atmos-phase/direct-publication-05/`.

Профилирование должно сравнивать весь DreamDaemon при одинаковых входах,
считая CPU основного потока, worker и процесса отдельно, private bytes,
выполненные расчёты и скользящий пик ТД. Работа C API по-прежнему занимает
основной поток; одно уменьшение времени DM-процедур не доказывает экономию
CPU процесса. Итоговые числа и ограничения приведены ниже.

## Вывод

Относительно прежнего Rust CPU на расчёт снизился на 9,6% при пожаре и
на 12,9% при плазме через трубы; CPU главного потока — на 9,9% и 14,1%.
Число значений публикации сократилось на 90,0% и 85,4%, время
`project_changes.total` — на 40,5% и 44,8%. FFI-вызовов стало больше:
сравнения baseline теперь идут через native API. Уменьшение CPU всего
процесса подтверждает, что выигрыш не ограничивается DM-профилем.

Относительно чистого DM CPU на расчёт: покой +15,3%, пожар −3,3%,
трубы −7,4%; главный поток: +13,9%, −5,6%, −12,7%. Небольшая разница
пожара предварительна: один захват не устанавливает эффект на фоне
изменяющейся фоновой симуляции. Одинаковые входы не гарантируют одинаковое
число вызовов всех фоновых объектов.

На трубах ТД почти не улучшился относительно прежнего Rust: 69,64% →
68,77%. Чистый DM проходит 60 игровых секунд за 69,14 с, итоговый Rust —
за 76,92 с, при 111 и 108 расчётах. Расчётов на реальную секунду меньше
DM на 12,5%. Пауза MC p99/max у DM — 63,9/94,9 мс, у нового Rust —
387,1/429,2 мс. Суммарный профиль подтверждает ускорение публикации,
но не распределяет конкретную худшую паузу между отдельными этапами.
Проблема длинных непрерывных этапов остаётся.

## Ограничения сравнения памяти

На трубах крупное транзитное выделение уже присутствует до нагрузки:
новый Rust начинает окно с 2148 MiB и заканчивает с 1888 MiB; старый —
с 1859 и 1902 MiB. У чистого DM тоже есть снижение: 1989 → 1718 MiB.
Причина освобождения не установлена. Разница пиков 281 MiB не доказывает
новую удерживаемую утечку; ни принудительная сборка, ни очистка не добавлялись.

В конце пожарного окна: DM 1716 MiB, прежний Rust 1882 MiB, новый —
1867 MiB. В конце покоя: DM 1706 MiB, новый Rust 1853 MiB.
Экономия относительно прежнего Rust на пожаре и трубах — примерно
14–15 MiB, предварительно. Это не изолированный замер размера baseline-пула.
Относительно DM остаётся около 147–169 MiB дополнительной памяти процесса.
Основная постоянная разница не устранена. Пики Rust с загрузкой превышают
2 GiB; требование удержать весь запуск ниже этого бюджета не подтверждено.
Начало и конец окна, RSS и пиковый commit сохранены в JSON.

## Допуск и воспроизводимость

Все принятые измеряемые окна без runtime. В DM-пожаре была одна известная
ошибка создания трупа за 69,1 с до окна: допуск по прежнему точному правилу
`corpse_organ_throw_after_delete`, без расширения исключений по пути файла.

Первый покой промежуточной версии исключён: после сохранения профиля
DreamDaemon упал при выгрузке `rust_g.dll`. Windows отметил
`rust_g.dll_unloaded`, коды C00001A5/C0000005, адреса 0065B640/006BA354.
Такая же сигнатура есть во вчерашнем чистом DM-контроле
`tmp/profiling/three-modes-dm-pipe-plasma-flood/`, без атмосферной DLL;
rust_g имеет тот же SHA. Захват не принят задним числом, библиотека и
политика ошибок не менялись. Повтор и финальные захваты завершились успешно.
События Windows и исходный отказ сохранены в JSON.

У `atmos-fire-before-01` был остановлен только диспетчер серии; сервер
и сборщик закончили контроль. Завершённый manifest проверен: capture()
проверяет нулевой код DreamDaemon, runtime и SHA бинарника. Неизвестный
код оболочки не выдаётся за измеренный код сервера; происхождение допуска
записано в attempts JSON.

Исходные захваты: `tmp/profiling/direct-publication-*`. Снимки исходников,
скрипт серии и проверки SHA: `tmp/atmos-direct-publication-01/`.
Серверы работали по одному; измеряемые окна не пересекались, тестов и
компиляций в этих окнах не было. CPU измерен только у целевого DreamDaemon.
Профилировщик включён во всех вариантах.

50+ игроков, длительный раунд, Linux и новый взрыв СМ на этом этапе
не проверены. Короткие захваты не доказывают отсутствие утечки за часы.
Общая цель миграции — снижение ТД и памяти под тяжёлой нагрузкой — пока
не достигнута. Публикация и CPU горячих сценариев стали дешевле, но текущий
Rust не выигрывает у DM по всем ресурсам. Коммит, push и PR не выполнялись.

## Средние за измеряемое окно

Средний ТД здесь — превышение реального времени над игровым: `(real / game - 1) × 100%`. Это показатель всего окна, в отличие от пика скользящего 10-секундного окна. Память усреднена по реальному времени интегрированием отсчётов ОС с интерполяцией на границах окна. Стартовые транзитные выделения включены.

| Сценарий | Средний ТД, DM → Rust | Средняя private, MiB, DM → Rust | Средняя RSS, MiB, DM → Rust |
| --- | ---: | ---: | ---: |
| Покой | 0.17% → 0.12% | 1705 → 1848 | 1678 → 1820 |
| Пожар | 3.23% → 1.25% | 1713 → 1863 | 1685 → 1840 |
| Плазма через трубы | 15.24% → 28.19% | 1832 → 2007 | 1810 → 1985 |

На пожаре среднее замедление ниже у Rust, хотя отдельные длинные паузы остаются. На трубах среднее замедление и средняя память выше DM. Один принятый захват на сочетание; различия малого размера предварительны.
