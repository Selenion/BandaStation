# Причина численных расхождений: теплоёмкость

Диагностика 2026-11-02, BYOND 516.1688, ветка `codex/rust-atmos-milla`.
По решению пользователя Rust приведён к наблюдаемому поведению BYOND.

DM вычисляет теплоёмкость через native `values_dot(moles, specific_heats)`:
`code/modules/atmospherics/gasmixtures/gas_mixture.dm:85`.
До исправления Rust умножал и суммировал `f32` в порядке добавления газов:
`rust/atmos/src/lib.rs:137`.

Проверка фактически прочитанных DM входных количеств показала **0 различий**
с исходными значениями после преобразования в float32 на всех 4405 сценариях.
Ошибка передачи количеств через JSON в этих входах не подтверждается.

Наблюдаемая семантика native `values_dot` на этих данных воспроизводится так:
обход газов в порядке таблицы метаданных, накопление произведения со сложением
с одним округлением в float32 на каждом шаге (эквивалент `mul_add`).
Это экспериментальный вывод о результатах API, не утверждение о конкретных
машинных инструкциях закрытого движка.

| Модель начальной теплоёмкости | Побитовых совпадений с BYOND |
| --- | ---: |
| Порядок таблицы + одно округление умножения-сложения | 4405 / 4405 |
| Порядок таблицы + отдельные float32 операции | 4026 / 4405 |
| Прежний порядок добавления + отдельные float32 операции | 3786 / 4405 |
| Вычисление суммы в float64 с округлением в конце | 3877 / 4405 |

Пример `vapor:random=2`; количества уже приведены к точным float32:

| Газ, в порядке добавления | mol | Удельная теплоёмкость |
| --- | ---: | ---: |
| zauker | 52.847408294677734 | 350 |
| helium | 83.99591064453125 | 15 |
| hypernoblium | 2.8620684146881104 | 2000 |
| water_vapor | 38.50178527832031 | 40 |

Результат прежнего Rust: **27020.7421875** J/K.
Native BYOND: **27020.740234375** J/K. Разница — один шаг float32.

Теплоёмкость участвует в пересчёте температуры, от которой зависят скорости
реакций. Такая разница может изменять прохождение точных проверок остатков
реагентов и накапливаться в последовательных циклах. После изменения только
этого расчёта в ядре все девять прежних расхождений исчезли на том же наборе
входов. Изменение не переставляет ключи смеси для планировщика реакций.

Рассмотренные варианты:

1. Воспроизвести наблюдаемую семантику BYOND в Rust. Сохранить текущую DM-модель
   как эталон. Порядок ключей смеси для планировщика реакций остаётся отдельным
   требованием; порядок суммирования теплоёмкости не должен его менять.
2. Согласовать новый общий расчёт для DM и Rust. Это изменит существующие
   численные результаты и потребует проверки влияния на игровой баланс и
   производительность DM.

Пользователь выбрал вариант 1. Использован `f32::mul_add` с обходом таблицы
метаданных. В коде оставлен комментарий о сохранении температур и ветвлений
реакций. Регрессионный тест проверяет битовые результаты двух смесей BYOND
при разных порядках добавления и сохранение исходного порядка ключей.

Повторная проверка на 516.1688: **4405 / 4405**, расхождений нет. Начальная
теплоёмкость проверяется побитно для всех входов. Допуски остальных численных
полей не изменены (relative/absolute 2e-5). Семь тестов Rust проходят.
Целевая BYOND 516.1685, стоимость расчёта в release и полный раунд ещё не проверены.

Диагностические артефакты: `tmp/diagnose_atmos.py`, `tmp/probe_precision.py`,
`tmp/atmos-diagnosis/`. Диагностика выполнена до исправления и сохранена для
воспроизведения причины. Актуальное сравнение — `tmp/atmos-oracle/report.json`.
Игровой DM-код и допуски сравнения не менялись.

## Подключение к миру: момент исполнения эффектов

При подготовке подключения выявлено отдельное ограничение пакетного интерфейса
`Outcome.effects`: исполнение всего списка после `Mixture::react()` меняет
игровое поведение. Это не расхождение численной химии, исправленное выше.
Исправление интерфейса пока ожидает выбора пользователя.

Реальный `/turf/open/hotspot_expose()` читает текущие `air.moles` и при O2<0.5
возвращается до создания hotspot. Поэтому нужно сохранить не только список
аргументов эффекта, но и состояние смеси в момент его исполнения.

Минимальный вход: открытый тайл, T=1644 K, plasma=1 mol, O2=0.51 mol,
hydrogen=1 mol. Порядок ключей — plasma, oxygen, hydrogen. Выполняются обычные
DM-реакции и оригинальная процедура принятия решения о hotspot из
`code/modules/atmospherics/environmental/LINDA_fire.dm`; конструктор объекта
hotspot заменён счётчиком в отдельном тестовом мире.

| Исполнение эффектов | Создано hotspots | Конечный O2 | Конечная T | Флаги |
| --- | ---: | ---: | ---: | ---: |
| Сразу в исходных точках DM | 1 | 0.495007455 | 2040.73804 | 5 |
| После всего пакета реакций | 0 | 0.495007455 | 2040.73804 | 5 |

Сначала plasmafire создаёт огонь, пока кислорода достаточно. Затем h2fire
опускает O2 ниже 0.5. Отложенные вызовы уже видят этот конечный состав.
Предыдущие 4405 сравнений регистрировали вызовы, а не исполняли эту проверку
реального мира; они продолжают подтверждать численную совместимость стенда.

Диагностика: `python tmp/diagnose_effect_timing.py`; результат
`tmp/effect-timing-diagnosis/effect-timing.json`. Изменений игрового кода и
Rust-ядра на этом этапе нет. Новая библиотека к SSair ещё не подключена.

Рассматриваемые способы устранения:

1. Сохранить исходные точки исполнения: Rust обрабатывает реакции и синхронно
   вызывает DM-эффекты на промежуточном состоянии смеси. Требует адаптации API,
   но сохраняет возможность пакетной обработки численной части.
2. Сохранить диспетчеризацию реакций и эффектов в DM, вызывая Rust для отдельных
   численных шагов. Меньше перестройка управления, но больше переходов DM↔Rust.

Рекомендация — первый вариант. Менять момент исполнения эффектов и игровую
логику без решения пользователя нельзя.

После этого пользователь запросил исследование текущего Paradise перед выбором.
Результат — `PARADISE_INTEGRATION.md`: обнаружен третий подход, с состоянием
горения и готовыми результатами в Rust, а не повторным исполнением старых
DM-проверок после пакета. Предыдущий выбор двух схем не охватывает этот вариант;
способ подключения пока не утверждён и не реализован.

Позднее пользователь выбрал перенос расчёта среды по образцу Paradise,
с обязательной фиксацией поведения Banda. Добавлены эталоны настоящего мира
и нативная обработка газовой части создания очага (`cell.rs`): она вызывает
повторную реакцию образца в исходной точке, до следующих кандидатов внешней
реакции. Все 14 текущих мировых примеров совпадают по проверяемой численной
части/командам. Реальное исполнение команд и полный тик ещё не подключены.

## Газообмен: сумма молей и перепад давления

В `transport.py` сохранены исходные процедуры `share/temperature_share` и
17 именованных эталонных сценариев; ещё 240 генерируются детерминированно.
После первого переноса 235/257 проходят прежний допуск 2e-5.

В сценарии `twenty_exchange_ticks` на шестом шаге газы и температуры
совпадают побитно, но BYOND `values_sum` возвращает 253.468140 mol,
Rust — 253.468155 mol. Результат формулы share различается:
0.257817775 против 0.25784373 kPa, то есть примерно 0.026 Pa.
Точный алгоритм native `values_sum` пока не установлен; простые варианты
суммирования вперёд/назад или через f64 не воспроизводят все 2418 измерений.
Диагностика: `tmp/diagnose_transport.py`, `tmp/transport-diagnosis/`.

После вопроса пользователь отметил, что подобные отклонения выглядят
пограничными и почти не влияют на игру. Согласован рабочий приоритет:
регистрировать их отдельно и продолжать независимый перенос; останавливать
его при изменении реакций, эффектов либо срабатывания игровых порогов.
Допуски и математика после обнаружения не изменялись. Подтверждения изменения
перемещения объектов в этом сценарии нет.

## Обратное влияние fire_act на продолжающуюся химию

Проверено двумя изолированными игровыми сценариями в
`world-feedback-reference.json`, захват `tmp/atmos-world/feedback-01/`.
В них вызывается оригинальный обработчик настоящего угля;
диагностический подкласс во втором сценарии лишь откладывает его вызов
до окончания внешнего `air.react()`. Обычный игровой код не изменён.

Вход: открытый пол, T=500 K, порядок газов hydrogen=1, plasma=10, O2=10 mol,
стопка 50 единиц угля. `coal/fire_act` выпускает `amount*10` mol CO2
при температуре воздействия, затем удаляет предмет.

| Исполнение fire_act угля | Конечная plasma | Расход plasma | Конечная T |
| --- | ---: | ---: | ---: |
| Сразу, как в Banda | 9.8132 mol | ≈0.1868 mol | 1548.25879 K |
| После внешней химии | 9.83790016 mol | ≈0.1621 mol | 1543.58655 K |

Расход плазмы меняется примерно на 13%. В обоих случаях флаги равны 5.
Это отличие последовательности игрового эффекта, а не микроскопическая
ошибка суммирования. Газ угля должен повлиять на последующие реакции того же
внешнего вызова, а не только на следующий тик.

Пользователю предложен выбор; исправление пока не внесено:

1. Перенос газовых действий предметов в Rust. Для полного сохранения поведения
   автономного расчёта нужно учесть не только прямые fire_act, но и сигналы,
   реагенты, разрушение и изменение геометрии. Уголь — простой частный случай.
2. Возврат в DM на таких действиях, применение исходной логики и продолжение
   Rust с изменённым воздухом/миром. Сохраняет предметную логику, но добавляет
   синхронизации; на массовом пожаре таких точек может быть много.

После просьбы пользователя раскрыть последствия изучены дополнительные пути:
`obj_defense.dm::fire_act` наносит повреждение и вызывает сигналы;
`combustible_flooder.dm` по сигналу выпускает газ и может менять turf;
`reagents_heated_on_fire.dm` нагревает реагенты;
`tanks.dm::atom_deconstruct` выпускает содержимое баллона;
`fuel.dm::burn_process` создаёт новые hotspot.
Поэтому описание «Rust считает, DM только оформляет» для всей этой границы
слишком узко: DM также сохраняет существенную игровую логику.

Предметы не требуется переносить разом: возможен поэтапный вариант с DM для
ещё не адаптированных взаимодействий. До завершения аудита такой вариант
остаётся гибридным. Текущая рекомендация для первой проверяемой версии —
вариант 2, затем перенос измеренных дорогих взаимодействий отдельно.
Пользователь ещё не выбрал, ни один из этих вариантов не реализован.

После вопроса о самом Paradise дополнительно прослежена цепочка предмета
`plasma/fire_act → atmos_spawn_air → blind_release_air → milla_safe`.
Paradise сохраняет предметную логику в DM и применяет газовые изменения между
native-тиками, перед следующим расчётом. Это отдельный вариант для Banda,
который не сохраняет автоматически исходную середину вызова react().
Детали и ссылки — `PARADISE_INTEGRATION.md`, раздел «Как Paradise возвращает
газ от предметов». Ни перенос всех предметов в Rust, ни остановка посреди
каждой реакции не являются обязательным устройством Paradise.

## Принятое решение: изменения мира между native-тиками

Пользователь выбрал этот порядок, как в Paradise. Предметная логика остаётся
DM, её обратное влияние на газ применяется между native-расчётами. Разница
с исходным порядком Banda в тесте угля теперь разрешена явно; старые данные
не перезаписаны, формулы реакций и численные допуски не менялись.

Реализованы native-владелец снимков/очереди, 32-битная DLL BYOND, безопасные
callback'и, исполнитель команд DM и gateway `assume_air` для явно привязанных
тайлов. Пройдены 12 сценариев настоящего мира через DLL и 11 проверок очереди
и времени жизни. Уголь проверяется с исходным обработчиком, без тестового
откладывания: фазовый порядок обеспечивает сама связка Rust/DM.

Это завершает выбор и реализацию данной границы. Полный перевод SSair,
газообмен, группы, многотиковый hotspot и адаптация остальных потребителей
воздуха ещё впереди. Подробности и граница покрытия — `PHASES.md`.

## Перепроверено: ошибка Rust в архивной теплоёмкости космоса

При переносе immutable/run_later зафиксирован отдельный исходный DM-набор:
`boundary-reference.json`, 14 сценариев по 20 тиков. Обычные прежние графы
по-прежнему проходят 38/38. Новый набор пока не является проверкой готовности.

Причина температурного расхождения установлена по коду:
`immutable_mixtures.dm:48` переопределяет только `space/heat_capacity()` и
возвращает `HEAT_CAPACITY_VACUUM=7000`. `heat_capacity_archive()` наследуется
от обычной смеси (`gas_mixture.dm:90`) и для пустого архива космоса возвращает
0. В новом прототипе `transport.rs::heat_capacity(archived)` ошибочно были
объединены оба расчёта: оба значения равнялись 7000. Ошибка исправлена;
различие пояснено комментарием и проверяется отдельным Rust-тестом.

`breach_floor_runs_first`: 100 mol O2 + 300 mol N2, 800 K, соседний настоящий
космос, порядок активных `[space, floor]`. После первого прохода газа нет
в обоих движках, T пустого тайла 800 K. Во втором проходе исходный DM сохраняет
800 K, прежний прототип давал ≈512.972 K. Это поле `air.temperature` пустой
газовой смеси, а не температура материала пола `turf.temperature`.

После возражения пользователя проверены текущие официальные исходники:
- tgstation `4b1be84802ffd6793c95f1b49108ba037aa07320`;
- BandaStation master `4f0a99fa092be6cdc605c563a10513830a80bf1e`;
- локальный BandaStation `a72025a0480566585ab7cc48a62873581fe3a6a5`.

`immutable_mixtures.dm` имеет одинаковое содержимое во всех трёх версиях
(SHA256 `dd035a2739b529d0d1757b7a13ea24d246b9cf8182247d1558d7604ac4a4f9bf`).
Процедуры архивной теплоёмкости обычной и turf-смеси также совпадают.
Поэтому формулировка «особенность вашего форка» и предложение выбирать
изменение физики были неверными: в этом месте нет различия Banda и tg,
нужно исправить реализацию порта в рамках согласованного сохранения поведения.

Дополнительно запущена **полная игровая сборка** без подмены газовых процедур:
`space_world.py --byond E:/Games/BYOND/bin --name verified-upstream-01`.
На BYOND 516.1688 получены `heat_capacity=7000`, `heat_capacity_archive=0`;
на обоих тиках после разгерметизации `air.temperature=800 K`, `moles=0`.
Совпадение с малым oracle подтверждено, runtime-ошибок нет. Полный отчёт,
хеши и логи: `tmp/atmos-space/verified-upstream-01/`.

2026-11-03 повторно проверен актуальный tgstation master
`1c7f0085a4025c14796ec1af42d007c217531d2c`: константа вакуума по-прежнему
7000, `immutable/space/heat_capacity()` возвращает её; архивная функция
наследуется от обычной смеси и даёт 0 для пустого архива. `immutable_mixtures.dm`
сохранил тот же SHA256. Это теплоёмкость газовой смеси вакуума; отдельное поле
материала `/turf/open/space.heat_capacity` равно 700000. Результат проверки
официальных файлов: `tmp/atmos-space/tg-master-verified-20261103.json`.

Набор запускается `network.py --boundaries --world-reference tools/atmos/boundary-world-reference.json`:
46/46 сценариев совпали с полным игровым эталоном и дополнительными случайными
инертными сценариями. Планетарная плазма теперь проверяется полной реализацией
создания очага, а не заглушкой. Отдельный полный проход огня и тепла зафиксирован
в `integration-world-reference.json`: 49/49 графов по 20 тиков совпали через DLL.

## Промежуточная отрицательная температура

Полный исходный DM в `two_space_boundaries` на первом тике получает −256 K
у пустого пола, включая архивную температуру; на следующем тике — TCMB.
Rust воспроизводит результат. Это конечное значение было ошибочно запрещено
адаптером при обратной передаче безопасной DM-смеси. Убрано ограничение знака
температуры в численном пакете; проверки конечности, объёма и газа сохранены.
Тест BYOND-адаптера закрепляет передачу −256 без изменения.

Подтверждение: полный исходный эталон `integration-world-reference.json`,
чистый прогон `tmp/atmos-phase/integration-14/`. Формулы газообмена и допуски
не менялись. `integration-11/12` сохраняют диагностику прежней ошибки пакета.

Эталон `complete-integration-01` не принят: фоновые игровые системы добавляли
тайлы за пределами заданного графа во время MC-resume. Он сохранён отдельно
в каталоге захвата. В принятом `complete-integration-02` очереди ограничены
явным набором тайлов перед каждой фазой и после неё; исходные газовые,
огневые и тепловые процедуры не подменяются.

## Наследование воздуха при замене пола — исправлено по решению пользователя

`/turf/open/ChangeTurf` при `CHANGETURF_INHERIT_AIR` переносит воздух, excited

## Отложенная инициализация при загрузке шаблонов — исправление проверяется

Полная MetaStation с opt-in адаптером зарегистрировала 780300 ячеек,
но затем загрузка стартовых шаттлов выявила преждевременный `finish_rebind`.

в (17,20,12), флаги 129. Новый открытый turf ещё не имеет `air`.

`reader.dm::build_coordinate` создаёт турфы при отключённом немедленном
Initialize; `map_template.dm` позже вызывает `SSatoms.InitializeAtoms`.
Обычный `ChangeTurf` не является гарантией готового воздуха в этом пути.
Адаптер до этого проверял немедленную замену и наследование воздуха.

Пользователь разрешил дождаться штатного `COMSIG_ATOM_AFTER_SUCCESSFUL_INITIALIZE`,
сохраняя физическую ячейку и версию. Сигнал подключён к существующему обработчику
жизненного цикла; при отложенной инициализации новая поверхность не передаётся
в Rust. После успешного Initialize импортируется её настоящая смесь. Закрытие
владельца освобождает подписку. Пока поверхность не готова, native-расчёт ждёт;
следующий расчёт получает настоящий номер цикла SSair, включая пропущенные номера.

Добавлены семь игровых проверок `deferred_world.dm.in` через настоящий режим
загрузчика SSatoms: отложенный воздух, запрет преждевременного расчёта, повторная
замена, завершение по сигналу, начальная смесь, возобновление и закрытие владельца.
Rust-тест проверяет реальные номера циклов после паузы. Семь проверок прошли
в `integration-20` вместе с 49 графами × 20 тиков и прежними мировыми проверками.

ошибки. Прогон выявил пропущенный runtime-пересчёт связности: перехват стоял
только в `init_immediate_calculate_adjacent_turfs`. Теперь оба пути вызывают
`topology_rebuilt`, включая обычный `immediate_calculate_adjacent_turfs`.
`world-01/02` сохранены и успешными полными прогонами не считаются.

## Оптимизация пустого состояния Rust

COW и отдельный 64-битный процесс не внедряются на этом шаге.
Первый шаг сохраняет формулы, f32, порядок газов и протокол ABI 8:

- Конструктор смеси не резервирует 20 ключей газов для пустого пространства.
- Результаты реакций выделяются при первой записи. `None` и `Some(0)` остаются
  разными значениями. Массив повторно используется при продолжающемся горении;
  история выделений не влияет на сравнение состояний и независимость копий.
- Парсер полного DM-пакета не создаёт массив результатов ради отсутствующих
  значений. Пакет и все его флаги присутствия остаются прежними.

Измерение i686 release `examples/layout.rs`:

| Поле | До | После |
| --- | ---: | ---: |
| Mixture | 312 B | 108 B |
| Cell | 360 B | 156 B |
| Tile | 232 B | 232 B |
| Два состояния, только встроенные поля, на z 255×255 | 73.42 MiB | 48.12 MiB |

Для 12 z это примерно 304 MiB на встроенных полях. Это не замер RSS:
активные результаты теперь занимают отдельную память, а таблицы, векторы,
команды и объекты BYOND учитываются отдельно. Удаление предварительного
резерва ключей дополнительно помогает при создании пустых смесей; его нельзя
автоматически умножать на два состояния, поскольку Clone копирует длину Vec.

54 теста Rust, Clippy и 4405/4405 сравнений химии с BYOND прошли.
`integration-27/world-06` недействительны: вызов `cargo run --example layout`
без `--features byond` перезаписал DLL библиотекой без экспортов BYOND.
Процессы остановлены, логи сохранены. Измерения их памяти не относятся к
Rust-симуляции. Добавлен короткий `native_probe`, проверяющий загрузку DLL и
ответ API до компиляции полной игры. Проверка приняла правильную DLL и
отклонила сохранённую неправильную. Повторы: `integration-28` и `world-07`.

Второй шаг: `GasAmounts` представляет нулевой массив молей без выделения
памяти, отдельно для текущего воздуха и архива. Первая запись выделяет
собственный массив; копии независимы. `clone_from` повторно использует массивы,
если они уже есть. Сохраняются отрицательный ноль, ключи газов, численные
снимки внутри реакций и порядок операций. Ни COW, ни другая точность не нужны.

| Поле, i686 release | До оптимизации | Итог второго шага |
| --- | ---: | ---: |
| Mixture | 312 B | 32 B |
| Cell | 360 B | 80 B |
| Tile | 232 B | 160 B |
| Два состояния, встроенные поля на z 255×255 | 73.42 MiB | 29.77 MiB |

Это размер встроенных полей, а не полное потребление процесса: непустые
массивы, таблицы, команды, объекты DM и накладные расходы считаются отдельно.
После второго шага прошли 56 тестов Rust, Clippy, 4405/4405 сравнений химии
и `integration-30` со всеми прежними сценариями и парным тестом контакта огня.

`world-07` после первого шага не упал по памяти, но не принят целиком:
стенд ошибочно ожидал один вызов `fire_act` при входе в огонь. Парная проверка
`contact_world.dm.in` установила одинаковые два вызова в исходном DM и Rust
(обычный и abstract Entered), ноль для cold fire. Исправлена проверка,
production-поведение не менялось. Полный обход карты в проверке отсутствия
DM-зеркала получил `CHECK_TICK`, чтобы сам стенд не вызывал Infinite loop.

`world-08` принят: полная MetaStation 255×255×12, 780300 ячеек, все 16 проверок,
ни runtime-ошибок, ни Infinite loop, ни падения по памяти. Частная память

`compare-rust-sm-01` не принят: после взрыва native operation 16 возвращает
`DetachedBinding`. Диагностический `compare-rust-sm-diagnostic-01` показал
готовые `/turf/open/space` с version=2, pending_rebind=TRUE, change_depth=1.
Диагностический прогон остановлен после воспроизведения; полное логирование
привязок удалено из production-кода и не входит в итоговую нагрузку.

Причина — разные условия в двух уровнях ChangeTurf. `/turf/open/ChangeTurf`
проверяет исходный аргумент path: `/turf/baseturf_bottom` не является
`/turf/open`, поэтому эта ветка не восстанавливает сохранённый воздух.
Родитель `/turf/ChangeTurf` разрешает placeholder в `/turf/open/space`.
Наш завершающий hook проверяет уже разрешённый path и ошибочно откладывает
завершение до восстановления воздуха, которого в этой ветке не будет.
Это не нехватка памяти и не неокончившаяся Initialize().

`integration-40` добавил два случая: явный `/turf/open/space` проходит,
`/turf/baseturf_bottom` оставляет depth=1 и проваливает ровно одну проверку.
Остальные 12 сценариев, 49 графов, очереди, API и панель проходят. Этот
прогон не принят как полностью успешный; на тот момент исправления не было.

В Paradise AfterChange вызывает initialize_milla/recalculate_atmos_connectivity;
API определяет ячейку по координатам:
[turf.dm](https://github.com/ParadiseSS13/Paradise/blob/5aca8afbcf00ef1f2bb96e179bf1389289551689/code/game/turfs/turf.dm#L407),
[api.rs](https://github.com/ParadiseSS13/Paradise/blob/5aca8afbcf00ef1f2bb96e179bf1389289551689/rust/src/milla/api.rs#L230).
Наши версии привязок дополнительно защищают Banda от старых команд.
По решению пользователя условие отложенного завершения теперь вычисляется
по исходной ветке восстановления воздуха, до разрешения placeholder.
Это сохраняет существующее DM-поведение газа и не требует нормализовать
path раньше, что само изменило бы выбор ветки наследования воздуха.
`integration-41`: все 16 проверок привязки прошли; отдельно проверены
завершение placeholder-замены и исходный тип воздуха космоса без прежнего
азота пола. Сохранение группы/таймеров обычной замены пола также проходит.

## Ошибка оборудования внутри общей фазы (2026-11-03)

Объединение машин обнаружило несовместимость обработчика исключений:
`finish_callback(..., failed = TRUE)` очищал все ещё не записанные изменения
фазы. Фокусный тест: первая машина добавляет 1 моль, вторая добавляет ещё 1
и выбрасывает исключение. Исходный DM сохраняет 102 моля, прототип оставлял 100.

В Paradise `bound_to_turf.set_dirty` сохраняет изменённые значения в DM-смеси;
`process_bound_mixtures` позже записывает dirty-смеси. В изученном SSair нет
отката этих значений при исключении машины. Это сопоставление кода, не запуск
аварийного сценария на Paradise.

Пользователь выбрал сохранение всех уже выполненных изменений, как Banda DM.
Общая фаза оборудования теперь вызывает `invoke(..., commit_on_error = TRUE)`:
изменения записываются перед передачей ошибки дальше. Остальные callbacks
сохраняют прежнюю политику обработки исключений. Новая проверка входит в
`exchange_error_contract`; эталон исходного DM не меняется.

Воспроизведение `tmp/atmos-phase/integration-exchange-error-01/exception-contract.json`
содержит локальный результат 102/100. Этот полный прогон не принят из-за
постороннего runtime `Qdeleted thing being thrown around` на хвосте при старте;
соответствующий игровой код по указанию пользователя не исправлялся.

## Общий helper создания газа после передачи владения Rust (2026-11-03)

World-owned тест настоящего угля выявил неперенесённый atmos_spawn_air:
в LINDA_system.dm он проверял `!air` и выходил, поскольку turf.air у владельца
Rust отсутствует. Прежние golden-проверки угля использовали малый регион
с DM-смесью и этот отдельный world-owned путь не проверяли.

Пользователь согласовал исправление общего helper через Rust API с сохранением
архивирования и активации Banda. Helper теперь использует has_turf_air и
get_mutable_air, сохраняя merge, archive и add_to_active. В ABI 11 архив
газа записывается обычным commit, а цикл и архив температуры пола — операцией 37.
Логика предметов не менялась. В Paradise аналогичный blind_release_air
передаёт merge через milla_safe/get_turf_air; direct turf.air не требуется.

При отложенной замене пола явный запрос архивирования сохраняется до привязки.
Восстановление группы первоначально перекрывало активацию helper; теперь
pending-control применяется после восстановления. Согласованные группа,
таймеры и версия привязки сохраняются. `integration-exchange-08`: полный
набор без runtime и расхождений, настоящий уголь создаёт 10 молей CO₂;
смеси, архивы, archived_cycle, температура пола и активация совпадают с DM
для обычного пола, космоса и CHANGETURF_INHERIT_AIR.

## Прерванная частичная публикация (2026-11-05)

Отбор служебных обновлений выявил разницу между предыдущим Rust-кадром и

## Воздух и очаги при удалении горящего пола (2026-11-05)

Полный `publish2-after-01-atmos-flood` обнаружил новый путь: разрушение пола
(80,174,2) удаляет очаг, настоящая топливная лужа в `COMSIG_QDELETING` создаёт
следующий. `has_turf_air()` ещё возвращает TRUE, но `get_mutable_air()` при
`pending_rebind` отдаёт `target.air = null`. `perform_exposure()` падает на
`environment.volume`. Исходный DM сохраняет воздух старого пола до замены.
Это отдельная несовместимость адаптера, а не исходная ошибка рам картин.

В Paradise физическая ячейка MILLA остаётся по координатам, а `AfterChange`
обновляет её режим и связность; аналога нашего запрета доступа через
`pending_rebind` там нет. Это сравнение архитектуры, не запуск того же
сценария топливной лужи на Paradise.

Пользователь выбрал предоставление старой смеси обработчикам удаления.
`read_pending_air` лениво читает её только для ещё инициализированного старого
пола внутри `ChangeTurf`. Временная смесь отделена от старых выданных ссылок;
новый и неинициализированный пол её не получает. При замене без обращения к
воздуху дополнительного чтения нет. Версия привязки и запрет старых записей
сохранены.

Сравнительный тест затем выявил второй согласованный дефект: созданный
лужей очаг пропускал регистрацию из-за `pending_rebind`. Газ уже совпадал,
но через четыре тика DM имел 0 очагов, Rust — 1. Пользователь выбрал подключать
оставшиеся очаги после замены пола, сохраняя управление жизненным циклом в
Rust. Отклонённый временной блокировкой конструктор теперь ставит флаг на
ячейке; после завершения привязки выполняется один локальный проход по
очагам этого тайла с проверкой версии. Такой же флаг обслуживает создание
очага внутри `sync_hotspot`, когда удаление предыдущего вызывает лужу.
Постоянной очереди ссылок и второго обработчика огня нет.

В Paradise `process_hotspots` / `update_hotspot` обслуживают отображение и
удаление DM-очагов по состоянию MILLA. Перенесён принцип согласования жизненного
цикла, а не их таймаут: здесь сохранены сроки Banda. Сравнение — по исходникам,
тот же сценарий на Paradise не запускался.

`tmp/atmos-phase/teardown-04/report.json`: 12 игровых сценариев, 49 графов по
20 тиков и прежние проверки прошли без runtime и расхождений. Новый F11
использует настоящую топливную лужу и сравнивает DM/Rust: космос напрямую,
космос через baseturf, наследование воздуха и пересоздание без замены пола.
Проверены полная смесь и архив, `fire_act` предмета с записью газа, сохранение
ячейки/версии, запрет старых ссылок и отсутствие ненужного чтения воздуха.
След очагов и расход лужи совпали на каждом из четырёх тиков: на космосе
очаг исчезает на втором тике, в сценарии без замены пола — на четвёртом.
Поведение закреплено как F11; исходные эталоны и допуски не менялись.

Полный повтор `tmp/profiling/teardown-flood-01`: 12285 полов, 60 игровых / 189.939
реальных секунд, новая DMB и та же DLL. В профиле 20 вызовов `read_pending_air`
и 394 `finish_rebind`; `null.volume` не повторился. DreamDaemon завершился с
кодом 0, но runner отклонил захват из-за 45 runtime рам картин и 6 водяного
бака при прочности ≤0. Рамы уже падали до F11; соответствие ошибки бака
исходному DM отдельно не проверено. Этот захват не подтверждает выигрыш CPU/RAM;
несвязанная логика повреждений не менялась. F11 проверен синхронным адаптером,
новый сценарий лужи отдельно в threaded-режиме не запускался.
