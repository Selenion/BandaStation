# Упрощение Rust-атмоса: проверка и нагрузка

Результат: свежесть сохранённых копий исправлена, тесты совместимости прошли. Относительно checkpoint уменьшились длинные блокировки MC, но устойчивой экономии CPU/RAM и преимущества над исходным DM серия не доказала. Считать оптимизацию завершённой нельзя.

Три независимых повтора на каждый вариант/сценарий без подробного proc-профилировщика. Отдельные шесть прогонов с профилировщиком используются для диагностики, их числа не усредняются с основной серией.

Checkpoint и текущий вариант различаются всем этапом упрощения: удалён неработающий конвейер, сохранён номер расчёта у эффектов, введён общий учёт выданных смесей, доставка порциями и обновление копий. Это сравнение этапа целиком, а не изолированное измерение одного нового обхода копий.

MetaStation, 780300 ячеек, BYOND 516.1688, одинаковые начальные входы и seed, 0 подключённых игроков. 30 игровых секунд прогрева и 60 игровых секунд рабочего окна. Серверы запускаются последовательно, сборки и другие тестовые серверы в измерительном окне не запускаются. CPU/private/RSS снимаются только с PID целевого DreamDaemon каждые 0,25 с; main определяется по исходному потоку процесса, worker — по его собственным CPU-счётчикам.

CPU — секунды процессорного времени за окно. Значения таблицы — медианы трёх повторов; пики ТД/MC/RAM — худшие из трёх. Средний ТД = (реальное время / игровое время − 1) × 100; пиковый ТД — максимум скользящего окна 10 игровых секунд. CPU/расчёт включает остальные подсистемы сервера, это не стоимость одного газового ядра.

Каждый столбец медиан считается отдельно: сумма медиан main и worker может отличаться от медианы общего CPU. В таблице отдельных запусков сохранены исходные значения.

На пожаре медиана CPU/расчёт: DM 138,9 мс, checkpoint 135,2 мс, текущий Rust 139,3 мс. Пониженный CPU за минуту у текущего Rust сопровождается 114–117 расчётами вместо 119–120 у DM. Это не ускорение симуляции. Худший интервал MC уменьшился с 154,8 до 109,1 мс, но у DM — 78,1 мс.

На плазме первые два текущих прогона дали 34,8–35,0 с CPU и 108–109 расчётов. Третий дал 52,9 с CPU и 69 расчётов: к концу появилось 1392 очага вместо 0–1. Он принят, сохранён в таблице и включён в медианы/пики. Это наблюдение более тяжёлого сценария; причина воспламенения и доля затрат новых обходов именно в этом запуске не установлены. Без отдельного профиля этого случая нельзя объявить причиной обновление копий.

В одинаково заданном вводе плазмы использованы 2545 труб и те же выходы/310800 mol. Но весь мир не детерминирован одним seed: перед окном зарегистрировано 296–343 pipenet, различаются фоновые объекты и последующее развитие пожара. Это повторяемая серия с одинаковым воздействием, а не строго одинаковая выполненная работа. Разницу в несколько процентов считать доказанной экономией нельзя.

В отдельном профилированном прогоне плазмы текущий Rust затратил 1,312 с total (0,793 с self) на 526 refresh_effect_readonly; process_effect_chunk — 14,607 с total на 622 вызова, project_changes — 8,013 с total. Эти времена вложены, складывать их нельзя. Обновление копий — измеримая дополнительная работа, но не единственная крупная статья: публикация и DM-эффекты сохраняют основную нагрузку главного потока. При росте числа порций повторные проверки накопленного набора могут дорожать; данных о числе проверенных смесей в плохом запуске нет.

Память текущего Rust в рабочих окнах обычно на 140–190 MiB выше исходного DM. Строгий предел процесса 2 GiB не выполнен на всех этапах: lifetime peak commit текущих Rust-процессов — 2090–2147 MiB, включая запуск; у checkpoint один рабочий пик достиг 2190 MiB. Среднее/RSS и разные пики не взаимозаменяемы. По короткой серии утечка не установлена.

Следующий шаг по данным: закрепить состав мира для контролируемого нагруженного теста и раздельно считать публикацию, эффекты, число порций и проверяемых копий. Без этого новый конвейер или массовое удаление совместимых путей лишь усложнят диагностику.

Число расчётов Rust считается по завершённым пакетам с эффектами. Число вызовов SSair и число заданий worker сохраняются отдельно: они не заменяют этот счётчик. На границе окна возможен один незавершённый кадр. Главный поток и worker не обязаны суммироваться в CPU процесса: остаются другие потоки.

Проверка совместимости: `simplification-readonly-02` — 9 проверок порций, 11 завершения, 11 времени жизни смесей, 5 номера кадра, 83 API, 31 worker, прежние 12 мировых сценариев и 49 графов / 980 шагов. Failures пуст; новых runtime нет. Один известный исходный runtime удаления органа сохранён без исправления. Сохранённая readonly-копия до нового API-запроса видит 58 mol, как живая смесь и свежий запрос.

Обновление копий проверяет только затронутые смеси с выданными копиями. При отличии копирует текущие/архивные газы, температуры, объём, результаты реакций и last_share. Обхода всей карты нет. В сохранённом Paradise 5aca8af readonly обновляется через set_dirty; прямые записи в Banda-список молей такие setter-уведомления обходят.

Непрофилированные окна явно останавливают и очищают ранний профиль Genesis. Проверяется отсутствие любых игровых proc-счётчиков; допускается только запись одного вызова очистки /world/Profile до окна, воспроизведённая отдельным минимальным тестом с DM-обёрткой. Непринятые измерительные запуски и завершения с ошибкой исключены; причины и сырьё сохранены.

Одна первая попытка текущего Rust на пожаре завершилась после окна с 0xc0000005; Windows указала rust_g.dll_unloaded. Она исключена, повтор того же бинарника принят. Аналогичное имя модуля уже встречалось в прежней серии, но причина сбоя не установлена и исправление не вносилось. Это отдельный риск завершения процесса, а не разрешённый исходный DM-runtime.

В штатный инструмент добавлен `--no-proc-profile`: явная остановка/очистка, проверка отсутствия игровых счётчиков, монотонная длительность окна, CPU/RAM каждые 0,25 с. Прошли 19 Python-тестов. Игровой smoke `simplification-tool-no-proc-01` скомпилирован без ошибок/предупреждений и завершился без runtime; профиль пуст. Это проверка инструмента на текущем коде без Rust, она не включена в сравнительные таблицы исходного DM.

Исходный DM: a72025a0480566585ab7cc48a62873581fe3a6a5. Checkpoint: c65fbacb60bddd493e079d4aa03456aae52dee64 с выключенным старым конвейером. Проверены все DM/DME эталонов против Git; отличия только в общих измерительных hooks. Оба Rust-варианта используют одинаковую принятую DLL с AVX2 и worker.

Не проверены 50+ игроков, полный длительный раунд, новые сценарии СМ/разгерметизации. Разброс трёх повторов и фоновые события ограничивают точность; исторические серии сюда не подмешиваются. Предел 2 GiB оценивается по фактическим пикам процесса, а не по размеру одних Rust-массивов.
