# Основные затраты Rust backend: аудит 2026-11-03

Здесь зафиксировано состояние до ABI 10. Последующие изменения и их проверки:
[EXCHANGE_OPTIMIZATION.md](EXCHANGE_OPTIMIZATION.md).
Последующая замена таблиц и проверка памяти: [MEMORY_OPTIMIZATION.md](MEMORY_OPTIMIZATION.md).

Цель переноса — экономия ресурсов на экземпляр сервера. Она пока не достигнута:
текущий backend требует больше CPU и памяти, чем исходный DM. Быстрый расчёт
в Rust пока перекрывается затратами адаптера и хранения состояния.

## Что измерено

Чистые парные захваты: MetaStation 255×255×12, BYOND 516.1688, rust-g 6.2.0,
Windows i686, без игроков; 30 игровых секунд прогрева и 60 секунд измерения.
DM — отдельная копия исходного HEAD, а не выключенный модуль в рабочей ветке.
Полные метрики: `tmp/profiling/COMPARISON-packed-01.{md,json}`.

| Сценарий | CPU DM / Rust, % одного ядра | Private DM / Rust, MiB, максимум | Проходов SSair | Реальное окно, s |
| --- | ---: | ---: | ---: | ---: |
| Покой | 13.34 / 18.11 | 1668.6 / 2475.9 | 120 / 120 | 60.11 / 60.29 |
| Поджог | 27.47 / 31.28 | 1697.0 / 2598.6 | 119 / 101 | 62.01 / 69.93 |

В покое CPU выше примерно на 36%, память — на 807 MiB. При пожаре память выше
на 902 MiB; CPU выше, хотя расчёт успевает выполнить меньше проходов.
Это отдельные захваты, не статистическая серия и не модель раунда с 50+ игроками.

Дополнительная инструментированная копия лежит в `tmp/atmos-cost-audit/rust`.
Она считает запрошенные живыми Rust-аллокациями байты, число выделений и время
внутри native-вызовов. Её результаты объясняют структуру затрат, но не заменяют
чистые замеры CPU: сами счётчики добавляют накладные расходы. Рабочее ядро
и игровой адаптер для этого аудита не изменялись.

## 1. CPU: публикация состояния дороже собственно расчёта

В чистом пожаре `compare-rust-fire-03`:

| Процедура | Вызовов | Включённое время, s |
| --- | ---: | ---: |
| `world_adapter.project_changes` | 606 | 5.300 |
| `cell.sync_air` | 80871 | 4.335 |
| `cell.refresh_cache` | 83664 | 2.582 |
| `phase.finish_callback` | 94832 | 2.536 |

Это вложенные времена: строки нельзя складывать. В исходном DM пожарный
`process_cell` занимает 6.282 s за 76040 вызовов, включая эффекты и вложенные
операции. Одна публикация нашего backend уже сопоставима с этим целым проходом.

В отдельном диагностическом пожаре `audit-rust-fire-01` получено 100 Rust-тиков:

| Внутри native 16 | Всего за окно, ms |
| --- | ---: |
| Подготовка/синхронизация второго состояния | 144.641 |
| `Schedule.tick`: физика, реакции, группы, очаги, тепло | 493.818 |
| Поиск изменившихся ячеек | 34.185 |
| Завершение/публикация состояния внутри Store | 17.928 |
| Весь native 16 | 694.783 |

Все native-операции вместе, без повторного сложения вложенных стадий,
заняли 1.579 s. Это время внутри экспортированной функции; обработка вызова
движком BYOND и выполнение DM снаружи в него не входят. Два захвата отличаются
планированием, поэтому их времена не составляют единого точного CPU-баланса.

Повторная диагностика покоя `audit-rust-idle-01` даёт только 71.443 ms
на 120 полных native-тиков (внутри `Schedule.tick` — 27.646 ms), а на все
native-операции вместе — 275.663 ms. Machinery в том же захвате — 2.395 s,
`invoke` — 2.510 s. Дальнейшая оптимизация одних формул не устранит этот разрыв.

Подтверждённый путь затрат:

1. `Frame.changed_cells` реагирует также на архивные циклы, таймеры, группы,
   давление и terrain, а не только на видимые изменения газа.
2. `world_adapter.project_changes` выгружает полный пакет каждого такого тайла.
   В пакет входят текущий и архивный составы и 52 числа результатов 26 реакций,
   даже если результаты пустые, плюс метаданные и состояние очага.
3. DM режет пакет на списки, декодирует смесь, обновляет существующий кэш,
   при наличии копирует readonly-снимок и вызывает обновление представления.

Первый кандидат — публикация по назначению: необходимые поля представления
и эффектов, инвалидирование кэша, полная смесь по фактическому запросу API.
Это должно сохранить все наблюдаемые поля Banda, а не просто удалить архивы
или проверки ради скорости. В этом аудите такой патч не вносился.

## 2. CPU в покое: слишком мелкие границы доступа объектов

В `compare-rust-idle-06` `world_adapter.invoke` вызван около 110 тысяч раз
за окно и занимает 2.509 s. Сглаженная стоимость machinery в конце:
19.506 ms против 7.486 ms у исходного DM. Это стоимость прохода, не сумма CPU.

`process_atmos_machinery` оборачивает каждый объект отдельным callback.
`borrow_air` добавляет полученную смесь в `working_mixtures` и помечает тайл;
внешний `finish_callback` делает полный commit для каждой взятой смеси,
даже если вызывающий код фактически оставил её неизменной. При пожаре
диагностика насчитала 74886 commit; сами Rust commit заняли только 360.552 ms,
сборка DM-пакетов и границы вызовов учитываются отдельно.

Второй кандидат — общая безопасная фаза оборудования и учёт реального изменения
смеси с записью один раз на фазу. Нужны проверки прямых присваиваний полям,
вложенных обращений и порядка обратной связи эффектов: механически расширить
границу callback без этих проверок нельзя.

## 3. RAM: полная карта, два состояния, индексы

Перепись `audit-rust-fire-01` после окна:

| Данные | Объём |
| --- | ---: |
| Живые запрошенные Rust-аллокации | 457.71 MiB |
| Ячейки и Tile в каждом из двух состояний | 780300 + 780300 |
| Из них Boundary::Space в каждом состоянии | 679448, около 87% |
| Непустые газовые массивы текущей/архивной смеси, оба состояния | 17.14 MiB |
| Результаты реакций, оба состояния | менее 0.1 MiB |
| Живые DM-кэши смесей | 10112 |

Полного DM-зеркала воздуха нет. Но Rust держит полный `Cell` 80 B и `Tile`
160 B на каждую координату дважды. Встроенный payload космических ячеек
составляет примерно 311 MiB, до накладных расходов таблиц. Это не обещанная
экономия: координаты, версии, тепловые поля и связи могут понадобиться и космосу.
В исходном DM `space/Initialize` присваивает общую static `space_gas`.

Отдельный микротест с текущими размерами записей показывает 372.37 MiB
для узлов двух пар Cell/Tile BTreeMap после уже выполненного уплотнения.
Реальная карта дополнительно хранит газовые массивы, версии, два координатных
индекса/реестра, очереди и команды. Из 457.71 MiB нельзя вычитать память процесса
и объявлять остаток размером DM: метрики описывают разные уровни аллокатора.

Особенность текущей архитектуры: мировой `run_tick` допускает только
синхронный расчёт, однако использует два полных состояния. Нет перекрытия
работы мира с фоновым расчётом, ради которого Paradise держит два буфера.
Выбор одного состояния с журналом либо настоящей асинхронной модели — отдельное
архитектурное решение; в этом аудите ни один вариант не реализован.

Остаток проверен Win32 HeapSummary в `audit-rust-idle-01` и
`audit-disabled-idle-01`. DMB, harness и диагностическая DLL совпадают по SHA256;
в контрольном захвате DLL используется только как наблюдатель, backend выключен.
Оба захвата прошли проверку runtime. Состояние после окна:

| Диагностическая метрика | Модуль выключен | Модуль включён |
| --- | ---: | ---: |
| Запрошенные живыми Rust-аллокациями байты, MiB | менее 0.001 | 460.78 |
| HeapSummary, занятые блоки всех heaps, MiB | 1434.56 | 2233.02 |
| HeapSummary, committed всех heaps, MiB | 1713.10 | 2668.98 |
| Private процесса, максимум в окне, MiB | 1681.82 | 2531.41 |

Дополнительные занятые блоки кучи — 798.46 MiB; сверх учтённых Rust-запросов
остаётся около 337.68 MiB. Их точное происхождение пока не установлено:
сюда могут входить объекты/списки и внутренние пулы BYOND, память других DLL
и накладные расходы. Это не доказанный размер полезных DM-объектов и не
доказанная утечка ссылок. Перепись 9081 DM-кэша в покое исключает полное зеркало
смесей, но не учитывает внутренние пулы движка.

Разность committed–allocated увеличивается ещё примерно на 157.43 MiB.
Это учёт свободного запаса/метаданных кучи, а не живые поля газов. HeapSummary
и private процесса имеют разные правила учёта: эти числа нельзя складывать
с 460.78 MiB и выдавать результат за точное разложение private.
При этом собственные Rust-запросы за минуту покоя выросли только на 30668 B,
а занятые блоки кучи — примерно на 28 MiB. Последующий аудит обмена должен
проверять и частоту создания списков/смесей, и удержание памяти после регистрации.

Артефакты: `tmp/atmos-cost-audit/summary.json`, оба `rust-audit-{before,after}.json`
и `dm-audit-{before,after}.json` в папках захватов. Воспроизводимый агрегатор:
`python tmp/atmos-cost-audit/analyze.py`. Instrumentation добавлена только
во временную копию DLL; её суммарный CPU нельзя выдавать за чистый результат.

Отдельно проверен простой путь передачи списков: 100000 вызовов native 9
с новым списком на каждый вызов в маленьком BYOND-проекте. После завершения
дополнительные занятые блоки — 2161 B (DM-контроль: 512 B). Простого удержания
каждого входного списка этот тест не обнаружил. Он не проверяет остальные
операции или большие пакеты настоящей карты. Артефакты:
`tmp/atmos-cost-audit/api_lists.{dm,py}`, `api-lists-summary.json`.
Определения счётчиков кучи: [Microsoft HeapSummary][heap].

## Как соответствующие места устроены в Paradise

Проверен master `5aca8afbcf00ef1f2bb96e179bf1389289551689` (актуальность SHA
перепроверена 2026-11-03). Paradise не запускался; это сопоставление исходников.

| Место | Banda prototype | Paradise |
| --- | --- | --- |
| Выгрузка в DM | Любая изменённая запись целиком | `InterestingTile` по причинам DISPLAY/HOT/WET/ICY/WIND; численное изменение само по себе не требует отправки |
| Кэш смеси | Обновляется при публикации, дополнительные readonly-копии | Ленивое чтение по номеру тика; обновление смеси при DISPLAY либо фактическом запросе |
| Оборудование | Callback и commit на внешней границе каждого обращения | Общая safe-фаза, прямой `process_atmos`; dirty-смеси записываются в конце фазы |
| Карта | Две пары BTreeMap Cell/Tile плюс индексы | Два плотных массива Tile по z, прямой индекс координат |
| Расчёт | Мировой расчёт синхронный | Фоновый расчёт, потоки по z, затем переключение буферов |

Paradise тоже передаёт полный 21-полевой пакет Tile внутри InterestingTile
(25 значений с координатной ссылкой/причинами/ветром), а не одни флаги.
Главное отличие — отбор тайлов и порядок работы DM, а не отсутствие обмена.
[Публикация и оборудование][ssair], [формирование interesting][interesting],
[ленивый воздух][readonly].

Проверка layout извлечённых полей Paradise на i686 даёт Tile 256 B при восьми
газах: два буфера на нашу геометрию требуют около 381 MiB только под Tile.
Гипотетическое увеличение GAS_COUNT до 20 при тех же per-gas flow массивах
даёт 512 B и около 762 MiB. Это модель размеров, не RAM работающего Paradise.
Артефакт: `tmp/atmos-cost-audit/paradise_layout.{py,rs,json}`.
Прямое копирование такого хранения не является гарантированной экономией.
[Поля модели][model], [копирование буферов и потоки][tick].

## Приоритет следующей работы

1. Сократить полную публикацию и копирование смесей Rust→DM.
2. Объединить безопасные обращения оборудования, убрать записи неизменённого воздуха.
3. Уменьшить постоянное хранение пассивного космоса и обосновать второй мировой
   буфер; отдельно проверить удержанную кучу после массовой инициализации.
4. Только затем рассматривать микровычисления и параллелизм. Потоки могут
   разгрузить главный поток, но не доказывают уменьшение суммарного CPU.

Каждый шаг требует прежних проверок поведения и чистых парных замеров покоя,
поджога и доступного сценария СМ. До выигрыша над исходным DM оснований
включать backend ради экономии инфраструктуры нет.

Не проверены живой раунд с 50+ игроками, производительность самого Paradise
и Linux. СМ остаётся диагностикой с ранее зафиксированными runtime: сторонние
ошибки игры по указанию пользователя не исправлялись.
