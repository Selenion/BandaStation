# Архитектура атмосферики Paradise и применимость к BandaStation

Последующее решение пользователя и реализация фазового обмена —
[PHASES.md](PHASES.md). Ниже сохранён исходный архитектурный разбор.

Исследовано 2026-11-02. Зафиксированный master Paradise:
`5aca8afbcf00ef1f2bb96e179bf1389289551689`.
Это разбор исходников, без сборки, запуска и измерения производительности Paradise.
Игровой код BandaStation и экспериментальное Rust-ядро при этом не менялись.

## Вывод

MILLA переносит в Rust целый расчёт среды тайлов: газообмен, теплопередачу,
химию, состояние очагов, конденсацию и определение необходимых игровых эффектов.
DM сохраняет оборудование, трубопроводы, дыхание, суперматерию, объекты мира
и применение результатов симуляции. Граница проведена через владение состоянием
и фазы доступа, а не через обёртку вокруг отдельных формул реакций.

Код даёт основания ожидать разгрузку главного потока BYOND. Он не доказывает
снижение общего CPU процесса или RAM: MILLA использует потоки по z-уровням,
плотные массивы и два полных буфера. Для нашей задачи сокращения инфраструктуры
эти две группы метрик нужно измерять отдельно.

Для Banda полезна архитектура MILLA. Прямое копирование её физики меняет
существующую игру: различаются газы, реакции, конденсация, очаги и вертикальные
связи. Способ устранения несовместимостей пользователь ещё не выбрал.

## 1. Кому принадлежит состояние

Rust хранит `Tile`: фиксированный массив восьми газов, тепловую энергию,
собственную теплоёмкость тайла, направленную теплопроводность и герметичность,
скорость потока, промежуточные потоки каждого газа, температуру/объём hotspot
и количество прореагировавшего топлива. Температура выводится из энергии
и теплоёмкости. `GasSet` кэширует общее число молей и теплоёмкость;
изменение состава делает оба кэша неактуальными. [Модель][model], [кэши][cache].

Тайлы находятся в плотных массивах `255 × 255`. Два `Model` содержат старый
и следующий кадр. DM может читать завершённое состояние, пока Rust рассчитывает
новое. Для отдельного z используются блокировки, а не блокировка каждого тайла.
После завершения всех z буферы переключаются. [Буферы][buffers], [тик][tick].

DM-смесь тайла создаётся лениво, когда она нужна вызывающему коду. Обёртка
`bound_to_turf` запоминает номер прочитанного тика и признак изменений.
В Rust записываются только изменённые смеси из списка обращений текущей фазы.
Это не копирование всех газовых DM-датумов карты каждый тик.
[Доступ][access], [запись изменений][dirty], [DM-смесь][bound].

## 2. Полный цикл

Упрощённый порядок между запусками Rust:

```text
Завершение Rust → переключение буферов → уведомление DM
  → разрешённые отложенные операции с воздухом
  → строительство/обработка трубопроводов
  → атмосферное оборудование (суперматерия после остального оборудования)
  → результаты предыдущего расчёта: изображения, вода/лёд, нагрев, ветер
  → обслуживание объектов hotspot и ветра
  → запись изменённых DM-смесей обратно в Rust
  → обновление pressure HUD
  → запуск следующего расчёта Rust
```

DM-фазы учитывают бюджет Master Controller и могут продолжаться на следующем
вызове. Новый Rust-тик не запускается, пока предыдущий не закончен или есть
спящие задачи, которым нужен изменяемый воздух. Кроме того, применяется
`self_wait = 0.15 SECONDS`; это собственный ритм Paradise, не настройка для
автоматического переноса в Banda. [Планировщик][scheduler], [синхронизация][sync].

В Rust запускается внешний поток, а внутри тика создаётся по рабочему потоку
на каждый выделенный z-уровень. Это не постоянный пул. Все рабочие потоки
завершаются до переключения буферов. На каждом z:

1. Полностью скопировать старый буфер в следующий.
2. Если уровень не заморожен: определить стены по кэшированным направлениям,
   обновить ветер и рассчитанные потоки газов.
3. Решить перенос газов и энергии итерациями. Первый проход идёт по всему
   уровню, следующие — по набору клеток со значимыми изменениями и их соседей.
   Остановка по порогам сходимости, предел — 100 итераций.
4. Обработать режим тайла, теплопроводность, реакции обычного воздуха
   и hotspot, конденсацию; ограничить некорректные численные значения.
5. Сформировать `InterestingTile` для нужных DM-действий.

Даже замороженный z сначала копируется. Набор активных клеток ускоряет
последующие итерации решателя, но не отменяет полные проходы остальных стадий.
Называть MILLA системой, которая вообще не обходит спокойные тайлы, неверно.
[Потоки и стадии][tick], [итерации][flow], [после газообмена][post].

## 3. Что действительно считается в Rust, что остаётся DM

| Участок | Rust | DM |
| --- | --- | --- |
| Газообмен | Давление, диффузия, ветер, перенос газов и энергии | Перемещение игровых объектов от ветра |
| Связность | Использует кэш герметичности/теплопроводности | Проверяет `CanAtmosPass` и обновляет кэш при изменениях мира |
| Тепло | Энергия воздуха/тайла, направленная теплопроводность, hotspot | `temperature_expose` тайла и заинтересованных объектов |
| Химия среды | Agent B, распад N2O, горение плазмы и H2 | DM `gas_mixture.react()` также остаётся для смесей вне этого Rust-цикла |
| Очаг | Температура, объём, расход топлива, обмен с обычным воздухом | Жизненный цикл объекта, изображения и взаимодействия с объектами мира |
| Вода и лёд | Удаляет сконденсировавшийся водяной пар, выдаёт WET/ICY | `MakeSlippery`, мокрый/ледяной пол и его игровая логика |
| Трубопроводы и приборы | Хранит воздух окружающего тайла | Сети, насосы, скрубберы, крио, термомашины и их газовые смеси |
| Дыхание, суперматерия | Предоставляет состояние среды | Расчёт в `milla_safe` между Rust-тиками |

Связность обновляется через `recalculate_atmos_connectivity()` и безопасную
задачу; Rust не вызывает `CanAtmosPass` на каждом соседстве. При этом его
`find_walls` всё равно обходит карту, используя уже подготовленные маски.
[Связность][connectivity], [стены и ветер][walls].

Трубопровод вызывает `reconcile_air()`, только если установлен `update`.
Дыхание и суперматерия явно обёрнуты в `/datum/milla_safe`; это не произвольное
вмешательство DM в работающий native-расчёт. [Трубы][pipes], [дыхание][breath],
[суперматерия][sm], [DM-химия][dmreact].

## 4. Эффекты: почему это шире горения

`InterestingTile` содержит копию рассчитанного состояния и флаги
`DISPLAY`, `HOT`, `WIND`, `WET`, `ICY`. Список передаётся плоским пакетом
через ByondAPI. DM обрабатывает только отмеченные причины. Это не вызов
DM после каждого шага реакции. [Формат][interesting], [получение][apiinteresting],
[применение][effects].

### Конденсация и лёд

Rust вычисляет давление насыщения по формуле Arden Buck, отдельно выше
и ниже 273.15 K. Если относительная влажность >1 и водяного пара >1 mol,
убирается избыток пара. Возвращается WET выше 273.15 K, иначе ICY.
DM делает соответствующий пол скользким. Комментарий в `do_turf_effects`
прямо объясняет цену альтернативы: вызов BYOND из рабочего потока означал бы
ожидание главного потока на каждом таком тайле. [Конденсация][condensation].

Важная деталь исходника: после прибавления `WATER_VAPOR_BREAKDOWN_ENERGY`
поле энергии сразу перезаписывается как `cached_temperature * heat_capacity`.
Поэтому считать, что эта прибавка сама повышает конечную температуру, нельзя.
Здесь фиксируется фактическая последовательность, без предложения исправления
Paradise и без переноса формулы к нам.

У Banda другая механика: реакция водяного пара требует соответствующий holder,
использует пороги 303.15/200 K и расход 0.25 mol за реакцию. `freeze_turf()`
добавляет заморозку предметам, может наложить статус на холодного моба и создаёт
permafrost. `water_vapor_gas_act()` также воздействует на слаймов и смывает
загрязнение/радиацию. WET/ICY Paradise этого контракта не заменяют.
[Наши реакции](../../code/modules/atmospherics/gasmixtures/reactions.dm#L96),
[наши действия тайла](../../code/game/turfs/open/_open.dm#L540), [пол Paradise][wet].

### Очаги, тепло и прочие последствия

У Paradise расход топлива и состояние очага уже рассчитаны в Rust. DM создаёт
и поддерживает объект по этим данным. Для множества очагов интервалы обновления
изображений увеличиваются и распределяются по тикам; гашение объекта имеет
небольшую задержку. Проверка кислорода Banda внутри `hotspot_expose` здесь
повторно не выполняется. Нагрев тайлов и объектов остаётся DM-действием.
[Очаг][hotspot], [применение HOT][effects].

У Banda конструктор hotspot вызывает `perform_exposure`, который может забрать
образец воздуха, снова вызвать `react()` и вернуть смесь. Кроме того,
`fire_act()` затрагивает содержимое тайла. Поэтому перенос только решения
«создать объект» не устраняет всю несовместимость.
[Наш hotspot](../../code/modules/atmospherics/environmental/LINDA_fire.dm#L98).

| Семейство эффектов Banda | Что есть в MILLA | Что требуется проверить у нас |
| --- | --- | --- |
| Вода/заморозка | Нативная конденсация + WET/ICY | Условия расхода воды, предметы, статусы, слаймы, очистка, флаги реакции |
| Hotspot | Нативное состояние + DM-объект | Промежуточный состав, повторные реакции при создании/обработке, нагрев объектов |
| Горячий лёд | Аналога в этом цикле нет | Создание предмета и RNG, holder, порядок появления |
| Радиация | Эти реакции отсутствуют | Момент импульса, дальность, порог и состояние мира |
| Halon resin | Реакции halon нет | Проверки существующих foam/resin, создание пены и последствия для связности |
| Ядерные частицы и галлюцинации | Эти реакции отсутствуют | Число частиц, RNG, порядок эффектов и воздействие на мобов |

Это карта обязательств, а не утверждение, что для каждой строки уже
воспроизведена ошибка. Подтверждённый пример потери момента создания огня
описан в [COMPATIBILITY_FINDINGS.md](COMPATIBILITY_FINDINGS.md).
Полный список наших реакций — [REACTIONS.md](REACTIONS.md).

## 5. Как обеспечен безопасный доступ из игры

- `get_readonly_air()` читает завершённый кадр; попытки изменять readonly-смесь
  запрещены. Во время native-тика это данные предыдущего завершённого расчёта.
- `blind_release_air()` / `blind_set_air()` позволяют поставить добавление
  или замену воздуха, когда не нужно предварительно его читать.
- Изъятие/изменение текущего воздуха выполняется через `/datum/milla_safe`:
  callback получает изменяемую DM-смесь только в разрешённой фазе.
- Нельзя сохранять эту смесь для последующего использования или спать внутри
  обычного callback. Вариант `milla_safe_must_sleep` специально задерживает
  следующие native-тики до завершения таких задач.

Следствие для Banda: заменить `react()` и несколько геттеров недостаточно.
Нужно проверить все прямые обращения к `air.moles`, внешние источники газа,
изъятие/возврат образцов, смену turf, изменение дверей и статусы объектов.
Отложенность callback меняет и момент, когда вызывающий код видит результат.
Это отдельный контракт совместимости, не деталь FFI.
[Реальный API][access], [задачи][sync], [руководство Paradise][guide].

## 6. Конкретные оптимизации и их цена

| Механизм | За счёт чего сокращается работа | Цена / предел |
| --- | --- | --- |
| Весь расчёт среды в Rust | Основные циклы не исполняются DM-интерпретатором | Перенос всей модели и её побочных эффектов |
| Распараллеливание по z | Главный поток освобождён от численного тика | Больше одновременно работающих потоков; общее CPU не обязано уменьшиться |
| Плотные массивы, фиксированные газы | Меньше словарных поисков в горячих циклах | Память выделена для всех клеток и газов |
| Кэши молей/теплоёмкости | Повторные запросы не пересуммируют неизменённый состав | Нужно корректно инвалидировать при каждой записи; порядок округления важен |
| Кэш связности | Нет вызовов сложной DM-геометрии на каждом газообмене | Все изменения дверей/тайлов должны обновлять кэш |
| Итерации только в меняющихся клетках | После первого полного прохода локальная работа | Полные проходы и максимум 100 итераций остаются |
| Пакет интересных тайлов | Меньше переходов между Rust и DM | Горячие тайлы могут оставаться интересными каждый тик; это не только изменения |
| Ленивые DM-смеси + dirty-запись | Не выгружается весь native-мир в DM | Два представления состояния и строгие правила доступа |
| Давление/маска газов для приборов | Не нужен полный воздух для очевидного раннего выхода | Данные снимка; нужны оговорённые правила актуальности |
| Более редкие изображения массового огня | Меньше DM-работы на представление | Не переносит из DM прочие воздействия на мир |

В начале каждой возобновлённой фазы оборудования SSair пакетно получает
давление и маску присутствующих газов наблюдаемых тайлов. Вентиляция без
необходимости подкачки и скруббер без подходящих газов выходят до получения
полной смеси. Если фаза прервалась, снимок запрашивается заново при продолжении.
Это полезный образец уменьшения постоянной работы приборов.
[Наблюдаемые тайлы][watched], [вентиляция][vent], [скруббер][scrubber].

### Память

Есть два массива по 65 025 `Tile` на каждый выделенный z. `init_to` выделяет
все уровни до запрошенного включительно; `Tile` выровнен на 64 байта.
Интересные тайлы дополнительно содержат копию `Tile`. [Модель][model],
[выделение][buffers], [результаты][interesting].

В текущей двумерной модели данные на один газ: 4 байта количества плюс
`2 axes × 2 directions × 4 bytes = 16` байт промежуточных потоков.
Расширение с 8 до наших 20 газов добавляет к объёму этих полей:

```text
(20 - 8) × (4 + 16) × 255 × 255 × 2 = 31 212 000 bytes ≈ 29.8 MiB / z
```

Это расчёт данных полей при сохранении схемы хранения. Он не равен приросту
`size_of::<Tile>()` с padding, RSS процесса или полной памяти сервера.
Добавление вертикальной оси отдельно увеличит потоки и соседства. Экономия
на DM-датумах может компенсировать часть затрат, но без замера знак итогового
изменения RAM неизвестен. Копирование целого уровня каждый тик также расходует
пропускную способность памяти даже при спокойной атмосфере.

## 7. Несовместимости прямого переноса

1. **Газы и химия.** У MILLA восемь фиксированных газов и четыре ветви
   химии среды, у нашего каталога 20 газов, 23 обычные и 3 электрохимические
   реакции. Отличаются теплоёмкости, стехиометрия, пороги и пересчёт температуры
   между реакциями. Наши формулы и порядок уже проверяются отдельно;
   замена их формулами Paradise не является совместимым переносом.
   [Константы][constants], [химия][chemistry].
2. **Вертикальный газообмен.** В MILLA две оси и четыре горизонтальных
   направления; работники z независимы. Banda использует `cardinals_multiz`,
   `UP/DOWN` и проверку прохода между уровнями. Одно расширение списка газов
   не сохраняет эту механику. [Оси][axes],
   [Banda multiz](../../code/modules/atmospherics/environmental/LINDA_system.dm#L64).
3. **Численная модель.** MILLA применяет итерационный перенос с ветром,
   свою модель hotspot, энергетическое хранение и очистку малых смесей.
   Это не построчный перевод `share()/process_cell()` Banda.
   [Решатель][flow], [hotspot][nativehotspot], [очистка][sanitize].
4. **Среда и тепло.** Space очищает газ/энергию, ExposedTo восстанавливает
   эталонную среду; Sealed пассивно охлаждается выше 293.15 K.
   Эти режимы, коэффициенты и ритм тика нельзя принимать за наши правила.
   [Режимы][modes], [теплопроводность][superconduct].
5. **Побочные эффекты и доступ.** Различия разобраны в разделах 4–5.
   Совпадения конечных молей и температуры недостаточно для проверки мира.

Новые причины несовместимости здесь только зафиксированы. Изменения формул,
фаз исполнения, multiz или игровых эффектов без решения пользователя не вносятся.

## 8. Что имеет смысл заимствовать и как проверять

Приоритет следует из нашего [исходного профиля](../profiling/BASELINE.md):
в пожарном прогоне `SSair/fire` занял 10.099 s, весь `gas_mixture.react()` —
1.391 s за то же окно. Это вложенные времена, их нельзя складывать.
Даже устранение всей стоимости `react()` затрагивает около 14% этого SSair;
одни арифметические формулы занимают ещё меньшую часть.

Рекомендация для дальнейшего обсуждения:

1. Использовать MILLA как образец границы между расчётом среды и игровыми
   действиями. Для тяжёлого сценария рассматривать газообмен и тепло вместе
   с реакциями и состоянием hotspot, сохраняя правила Banda.
2. До подключения согласовать контракт эффектов: что полностью рассчитывает
   Rust, какие действия DM могут менять смесь/геометрию, в каких точках
   требуется обратная связь. Перечень реакций использовать как проверяемую
   спецификацию; не считать существующие 4405 численных случаев полным тестом мира.
3. Постоянные расходы приборов исследовать отдельно: в тихом захвате финальная
   скользящая оценка `cost_atmos_machinery` была 7.77 ms, `cost_turfs` — 1.44 ms.
   Это не среднее за всё окно и не основание менять приборы без отдельного замера.
4. Не принимать плотные два буфера за готовую оптимизацию RAM. Выбрать хранение
   после подсчёта памяти на наших газах, реальных z и целевой разрядности BYOND.

Минимальный следующий этап проверки после выбора архитектуры:

- Сравнение DM/Rust по тикам: вакуум/разгерметизация, дверь/стена, вертикальный
  проход, перенос газа/энергии, пожар и гашение, конденсация/заморозка.
- Проверки мира: предметы и мобы в холодном/горячем тайле, изменение газа
  из hotspot, все восемь семейств текущих `Effect`, RNG и последовательность.
- Совместное изменение тайла дыханием, вентом, скруббером, внешним источником
  и суперматерией; чтение во время расчёта, выгрузка/смена turf, отсутствие
  потерянной записи и повторного эффекта.
- Повтор одинаковых сценариев на одинаковых BYOND/DLL: время главного потока,
  длительность полного атмос-тика, суммарное CPU всех потоков, private memory,
  working set. Затем раунд с 50+ игроками. Снижение лага не подменяет цель
  уменьшить потребление инфраструктуры.

Не проверены запуск Paradise, его CPU/RAM и поведение полного раунда.
В нашем сервере Rust по-прежнему не подключён к SSair; решений о несовместимостях
этот отчёт не реализует.
