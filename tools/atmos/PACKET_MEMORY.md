# Удержание пакетов на границе DM/Rust

Этот отчёт фиксирует этап исправления пакетов. Последующее изменение Rust-хранения
и актуальные замеры: [SHARED_SPACE_MEMORY.md](SHARED_SPACE_MEMORY.md).

BYOND 516.1688, Windows i686, ABI 11. Формулы, структура Rust, порядок
эффектов и протокол не меняются. Рабочая DLL остаётся прежней:
`553671f5656e8462a20df22a2356a281613bf6dcbc633a93e1b76cba2a9dda12`.

## Что установил профайлер

После прежнего уменьшения Rust-хранения оставалась необъяснённая память
всего DreamDaemon. Для поиска подключён [heob 4.2][heob]: он сохраняет стеки
ещё не освобождённых CRT-выделений. Это учёт удерживаемой памяти, а не
автоматическое доказательство утечки каждого показанного блока.

MetaStation, 780300 ячеек: история очищена непосредственно перед созданием
Rust-владельца. После регистрации профайлер показал 295.18 MiB новых
удерживаемых выделений BYOND; 266.09 MiB из них — буферы списков у одного
внутреннего адреса realloc. Среди стеков непосредственно виден Byond_WriteList.
Дальние имена BYOND приблизительны: закрытый движок не предоставляет полных
символов. Точный DM-путь подтверждён отдельным воспроизведением ниже.

Первый снимок сбрасывает историю heob. Последующий снимок после загрузки
шаттлов и 30 игровых секунд содержит ещё 114.30 MiB новых удерживаемых
выделений, включая обычную инициализацию игры. Все эти байты нельзя целиком
приписывать атмосу. SVG накапливает несколько снимков: их нельзя складывать
как одновременно живую память. Число листовых выделений последнего снимка
сверено с отдельным счётчиком: 165486 / 1716648.

Обычный heob исчерпал адресное пространство до регистрации атмоса. Для
диагностики собран вариант того же тега с PTRS=8 вместо 128; защита страниц
отключена через `-p0`. Алгоритм учёта не менялся, глубина стеков ограничена.
У heob без консольного stdin сбрасывается `-k1`, поэтому маленький helper
явно очищает историю при первой отметке перед Rust. Снимки получены через
официальный heob_control; при копировании проверена завершённость SVG.
Игра завершилась с кодом 0 и без runtime. Размер процесса и CPU под heob
не используются как результат оптимизации.

Запуск: `tmp/profiling/heob-world-04`, исходники диагностики
`tmp/heob-world-01.py`, `tmp/heob-world-04.py`, `tmp/heob_summary.py`,
`tmp/profilers/heob/control.c`. Предыдущие неудачные запуски не включены
в чистые сравнения. Rust System allocator использует другой путь выделения:
его живые запрошенные байты учитывались отдельной диагностической DLL.

Повтор с исправленной обёрткой, `heob-world-05`, те же DLL и настройки:

| Удерживаемые CRT-выделения после регистрации | До, MiB | После, MiB |
| --- | ---: | ---: |
| Все новые выделения | 295.18 | 41.87 |
| Основной адрес realloc буферов списков | 266.09 | 11.80 |

Таким образом, исчезло около 253 MiB запрошенных удерживаемых буферов.
Количество ячеек в обоих состояниях после прогрева — 780300. Снимок после
прогрева содержит 90.05 MiB новых выделений вместо 114.30 MiB; он включает
также обычные объекты раунда и не является чистым размером пакетов.
Оба снимка сверены с отдельными счётчиками, игра завершилась без runtime.

## Причина и минимальное воспроизведение

Единая DM-обёртка native создавала список arguments и передавала его как
`call_ext(library, "byond:banda_atmos")(arglist(arguments))`.
На проверенной сборке BYOND после возврата сохраняются ссылки на пакеты.
Это воспроизводится и на чтении, и на успешной выдаче данных.

2000 вызовов в маленьком мире, одинаковая DLL и численные пакеты:

| Путь | Чтение: прирост allocated, B | Выдача: прирост allocated, B |
| --- | ---: | ---: |
| Прямой call_ext | 66180 | 73835 |
| Обёртка с arglist | 131165512 | 138908915 |
| Обёртка с явными аргументами | 66226 | 73881 |

Это Win32 HeapSummary allocated после цикла относительно начала, без
профайлера. Не private процесса и не размер Rust-модели. После освобождения
локальных ссылок большой прирост старой обёртки сохраняется. Живой Rust
в этих проверках остаётся около 1.3–3.7 KiB. Сценарий чтения намеренно
передаёт большой пакет с лишними полями и получает отказ в валидации;
сценарий выдачи использует успешный opcode 35.
Микрообёртка возвращает отказ без throw, чтобы завершить цикл; штатное
пробрасывание ошибок отдельно проверяет игровой harness.

Дополнительный успешный opcode 9 проверен по слабой ссылке на список:
при прямом вызове список исчезает, у старой обёртки остаётся, у исправленной
исчезает. Ссылка проверяется сразу после возврата, до повторного использования
освободившегося ID другим списком. Прежние маленькие проверки вызывали DLL
напрямую и потому не воспроизводили дефект рабочей обёртки.

Артефакты: `tmp/process-packets-01`, `tmp/process-packets-wrapped-01`,
`tmp/process-packets-fixed-01`, `tmp/packet-lifetime-02`,
`tmp/packet-lifetime-fixed-01`. Агрегаты и хеши:
[PACKET_MEMORY_RESULTS.json](PACKET_MEMORY_RESULTS.json).

## Исправление и Paradise

native выбирает прямой вызов по числу аргументов. Дополнительный список
arguments и args.Copy больше не нужны. Проверка результата, диагностика
ошибок и ограничение числа аргументов сохраняются. Пакеты не очищаются
принудительно: вызывающий DM продолжает читать результаты и сохранять
свои списки столько, сколько нужно.

В Paradise на проверенном SHA `5aca8afbcf00ef1f2bb96e179bf1389289551689`
[RUSTLIB_CALL][paradise] раскрывается в прямой call_ext с явными аргументами;
get_tile_atmos и set_tile_atmos используют этот макрос. Их arglist у
on_run относится к обычным DM-callback и не является этим путём вызова DLL.
Это сравнение исходников, не замер памяти запущенного Paradise.

## Поведение и замеры

`integration-packet-lifetime-01`: 12 мировых сценариев, 49 графов × 20 тиков,
13 проверок очередей/жизненного цикла, наследование пола, 16 привязок,
7 отложенных инициализаций, 32 API, контакт с огнём, 21 проверка панели,
обмен и общий gas-spawn helper. Расхождений и runtime нет.
Две новые проверки требуют освобождения входного и выходного пакетов после
возврата native; они включены в обязательный набор проверок harness.

Обычные запуски без heob: MetaStation, 30 игровых секунд прогрева и 60 секунд
измерения, без клиентов. Rust DLL та же, меняется только DM-обёртка.
Исходный DM — `a72025a0480566585ab7cc48a62873581fe3a6a5`.

Наблюдаемые максимумы private за весь запуск, включая инициализацию, MiB:

| Сценарий | Исходный DM | Rust до | Rust после |
| --- | ---: | ---: | ---: |
| Покой | 1937.0 | 2554.8 | 2239.0 |
| Поджог | 1967.0 | 2482.0 | 2285.0 |
| СМ, диагностика | 1968.8 | 2466.8 | 2246.9 |

Это максимумы отсчётов раз в секунду, не гарантированный мгновенный пик.
Предыдущие Rust-запуски исторические: фоновые объекты и состояние аллокатора
различаются. Все три имеют ту же рабочую DLL ABI 11 с блоками по 8. Снижение
пика процесса нельзя целиком и с точным процентом приписывать одной правке;
микровоспроизведение и heap-стеки отдельно подтверждают удержание пакетов.

В окне после прогрева:

| Сценарий | CPU DM / Rust, % ядра | Private peak DM / Rust, MiB | Проходы SSair DM / Rust | Окно DM / Rust, s |
| --- | ---: | ---: | ---: | ---: |
| Покой | 14.42 / 16.03 | 1680.4 / 1978.5 | 120 / 120 | 60.02 / 60.03 |
| Поджог | 31.09 / 29.91 | 1707.0 / 2004.9 | 120 / 106 | 60.04 / 66.25 |
| СМ, диагностика | 38.66 / 38.71 | 1691.6 / 1971.5 | 109 / 99 | 62.89 / 69.24 |

Покой и поджог прошли строгую проверку compare.py. Первый контроль DM для
пожара исключён из чистого сравнения из-за известного runtime рыбьего хвоста
при инициализации; повторный контроль чистый. СМ в обоих backend удалена
взрывом радиуса 35; входы инцидента совпадают, но runtime делают его
диагностикой. Помимо null.z и питания голодека, оригинальный DM обращается к
отсутствующей excited group; Rust пропускает её таймеры по прежнему решению
пользователя. В новом Rust-запуске также встретился бросок предмета с loc=null:
неизменённые throwing.tick → finalize → throw_impact не проверяют пустой
get_turf. Отдельное воспроизведение этого броска на полном DM не запускалось.
Несвязанные исходные участки не исправлялись.

Память остаётся выше исходного DM примерно на 278–318 MiB за весь запуск.
Повторная перепись Rust после исправления показывает 246.5 MiB живых данных,
из них около 182 MiB — Cell/Tile. Большинство записей — пассивный космос;
DM использует общую immutable-смесь. Это объясняет направление дальнейшего
сокращения, но не является точным разложением private между компонентами.
Прямое копирование хранения Paradise не решает этот расход: у него два
плотных буфера со своей моделью, см. [MEMORY_OPTIMIZATION.md](MEMORY_OPTIMIZATION.md).

Выигрыш CPU не доказан: в огне меньший процент сопровождается меньшим числом
проходов и более длинным окном. Стартовые pipenet DM/Rust — 296/332 в покое,
331/332 в огне; active turf — 103/101 в огне. По одному запуску нельзя
доказать точный процент экономии для раунда с игроками. Linux,
50+ подключённых игроков и длительный раунд не проверены.
