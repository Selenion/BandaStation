# Совместное хранение одинакового состояния космоса

Продолжение [PACKET_MEMORY.md](PACKET_MEMORY.md). Причина оставшегося расхода
проверяется на полной MetaStation, BYOND 516.1688, Windows i686, ABI 11.

## Профиль выделений

[heob 4.2](https://github.com/ssbssa/heob/tree/4.2) видит CRT malloc, тогда как Rust System вызывает HeapAlloc.
Для этого аудита собрана отдельная диагностическая копия Rust: System заменён
прокси через CRT malloc/free с сохранением выравнивания и семантики realloc.
Она считает исходные запрошенные Layout-байты; heob дополнительно видит
служебный заголовок и запас выравнивания. Рабочая DLL использует System,
не содержит этого прокси, счётчиков, вызовов HeapSummary и отладочного API.
CPU и private под heob не используются как результат оптимизации.

heob 4.2 x86 собран с глубиной стека 8 вместо 128 для ограничения собственного
расхода адресного пространства. Путь к PDB передан через -y. Запись начинается
непосредственно перед native-регистрацией: история очищается helper-вызовом
heob_control, так как -k1 сбрасывается без консольного stdin. После каждого SHOW
записанные флаги очищаются: второй снимок содержит новые удерживаемые выделения,
а не все живые данные. SVG содержит несколько секций; анализируется последняя,
число выделений сверяется с отдельным счётчиком до копирования снимка.

До изменения после регистрации 780300 ячеек живые запросы Rust занимают
256.64 MiB. В стеках heob крупнейшие выделения: страницы Tile — 121.30 MiB,
Cell — 61.02 MiB, узлы индекса координат — 23.89 MiB, привязок — 16.16 MiB.
Это CRT-размеры с заголовками диагностического прокси. Типизированный подсчёт
даёт 181.09 MiB страниц вместе с таблицами ссылок без прокси. После прогрева
два состояния занимают 246.75 MiB живых native-запросов; страницы — 181.92 MiB.
Следовательно, отсутствие DM-зеркала само по себе не решает расход: исходный DM в
code/game/turfs/open/space/space.dm:58 использует static immutable space_gas,
а Rust продолжал хранить отдельную полную Cell/Tile для почти каждого пустого космоса.

Артефакты до: tmp/profiling/native-heap-before-01. Исходники диагностической
копии: tmp/atmos-native-heap/before/rust; подготовка/запуск/анализ:
tmp/native-heap-world-prepare.py, tmp/native-heap-world-capture.py,
tmp/native-heap-analysis.py. Сырые данные и хеши сведены в сопутствующий JSON.

## Изменение хранения

После топологии общий drain_effects прежде запрашивал изменяемую Cell даже
при пустой очереди. Промежуточный профиль native-heap-after-01 показал
52.89 MiB повторных выделений Cell на этом пути: объединённые при регистрации
страницы снова отделялись. Теперь пустая очередь проверяется до get_mut;
выдача непустой очереди и обработка отсутствующей ячейки сохраняются.

При регистрации и замене пола сравниваются соседние полные страницы Cell по
8 записей. Полностью одинаковые страницы разделяют существующий Arc; при
любой записи get_mut, pair_mut, values_mut или remove отделяет нужную страницу.
Снимки и другие координаты остаются прежними. Отдельного реестра, глобального
поиска одинаковых значений и очистки кэша нет. Повторное объединение всех
страниц на каждом тике не добавлено.

В Tile координаты и тепловые соседи остаются отдельными для каждой ячейки.
Остальные поля вынесены в Arc<TileState>. Только полностью одинаковые состояния
с boundary=Space объединяются с предыдущим ID. Группы, таймеры, архивы,
давление, тип смеси, материал и флаги участвуют в сравнении. Изменение состояния
отделяет его через Arc::make_mut. Равная топология не присваивается заново,
чтобы не отделять пустые состояния при штатной регистрации связности.

Сравнение сохраняет биты float, в том числе знак нуля, порядок газов и наличие
нулевого результата реакции. Cell с hotspot или ожидающими командами не
объединяются. Планетарные TileState не объединяются. Формулы, порядок обработки,
число логических ячеек, координатные ID и версии привязки не меняются.

Цена: дополнительное обращение к Arc для Tile и отделение его состояния при
записи. На картах без одинакового космоса экономия меньше; полностью изменяемая
карта может потреблять больше из-за заголовков Arc и отдельного размещения.
Поэтому эффект проверяется на всей карте и обычной DLL без перехватчика malloc.

## Сравнение с Paradise

Проверен зафиксированный Paradise 5aca8afbcf00ef1f2bb96e179bf1389289551689:
[model.rs](https://github.com/ParadiseSS13/Paradise/blob/5aca8afbcf00ef1f2bb96e179bf1389289551689/rust/src/milla/model.rs),
[tick.rs](https://github.com/ParadiseSS13/Paradise/blob/5aca8afbcf00ef1f2bb96e179bf1389289551689/rust/src/milla/tick.rs).
Там координаты вычисляются из индекса массива, а физический Tile хранится
отдельно; состояние окружения также отделено от индивидуального тайла.
Но два основных буфера плотные, next.copy_from(prev) копирует Tile перед
расчётом. Такой интернинг одинаковых Cell/TileState в Paradise не найден.
Это адаптация идеи отделения координат от состояния к поведению Banda,
а не буквальный перенос их модели памяти. Измерений запущенного Paradise нет.

## Повторный heap-профиль

Оба полных профиля завершились с кодом 0, runtime нет. Между ними менялась
только реализация Rust; формулы и DM fixture прежние.

| Живое хранение, MiB | До | После |
| --- | ---: | ---: |
| Rust после регистрации | 256.64 | 131.19 |
| Rust после прогрева, два состояния | 246.75 | 122.29 |
| Страницы Cell/Tile, состояния Tile и таблицы ссылок после прогрева | 181.92 | 59.34 |

Почти 124.5 MiB живых native-запросов устранены. Ячеек по-прежнему 780300 в
каждом состоянии; космоса после прогрева 676236. Уникальных страниц Cell,
учитывая оба снимка, 13530 вместо 97578; страниц внешнего Tile — 97584,
но запись уменьшилась с 160 до 48 B. TileState занимает 112 B плюс заголовок
Arc и существует в 111472 уникальных экземплярах вместо отдельного состояния
на каждую координату. Размеры указаны для целевой i686, а не x64.

Следующие заметные блоки по стековым снимкам — внешние Tile-страницы около
37.2 MiB CRT, индекс координат 23.9 MiB и таблица привязок 16.2 MiB. Это
локализованные дальнейшие кандидаты, а не доказательство того, что каждый
такой байт можно удалить без замены. Paradise обходится прямым индексом
плотной координатной сетки; Banda Store также обслуживает маленькие графы,
удаление/добавление координат и стабильные ID. Эти индексы в данном изменении
не переписываются. Часть общих стеков обрезана глубиной 8 или объединена
компоновщиком; размер отдельных категорий не следует считать точным разложением
всей private memory DreamDaemon.

Из-за высокого CPU в первом новом покое после основных трёх сценариев
последовательно повторены старая DLL и новая DLL; код между запусками не менялся.

| --- | ---: | ---: | ---: | ---: | ---: |

| Повтор новой DLL | 16.05 | 1829.3 | 1793.6–1793.7 | 2091.0 | 296 |

Снижение private относительно свежего контроля — 167.3 MiB в окне и 160.1 MiB
по максимуму всего запуска. Относительно исходного DM повтор новой DLL всё ещё
выше по private: 1829.3 против 1680.4 MiB в окне, 2091.0 против 1937.0 MiB
за весь запуск. У новой DLL в двух чистых покоях CPU 20.79 и 16.05%; у старой
16.03 в историческом замере и 18.12 в свежем контроле. Стартовые pipenet у новой
331 и 296, у свежего старого контроля 332. Меньший CPU повтора нельзя целиком
приписывать оптимизации, как и больший CPU первого прогона нельзя уверенно
приписать Arc. Эти захваты не устанавливают устойчивый выигрыш/регрессию CPU.

В первом новом покое working set составлял только 954.2–959.1 MiB при private
1869.0–1873.4 MiB; в повторе резидентность стала сопоставима с контролем.
Причина этой разницы не установлена. Она не доказывает дополнительную двукратную
экономию физической RAM: working set зависит также от политики ОС. Основные
выводы опираются на private всего процесса и независимые живые Rust-запросы.
Все четыре результата покоя сохранены, первый чистый новый замер не удалён.

## Ограничения

Максимумы снимаются раз в секунду; короткие пики могут быть пропущены.
Одинаковый startup seed не устраняет расхождения последующих фоновых событий.
Рабочие private и live requested Rust не складываются: второе входит в первое.
Точное разложение оставшихся 149–193 MiB private между Rust, DM и удержанием
памяти аллокатора не установлено. Профиль локализовал основные native-блоки,
но не доказывает, что вся оставшаяся разница принадлежит одному из них.

Linux, 50+ игроков, другие карты и полный раунд не проверены.
Экономия инфраструктуры относительно исходного DM пока не подтверждена.
Коммита, push и публикации PR на этом этапе нет.
