# Что задерживает главный поток на плазме через трубы

## Подтверждённый результат

После выноса математики и прямой публикации уменьшилась стоимость CPU,
но вырос размер непрерывной работы главного потока. В исходном DM
`process_active_turfs` и `process_high_pressure_delta` проверяют
`MC_TICK_CHECK` после тайла. В текущем Rust-пути готовый кадр целиком
публикуется, затем выполняется весь пакет эффектов без проверки бюджета.

В новом диагностическом Rust-запуске худшая пауза между проходами MC —
390,6 мс при ожидаемом игровом шаге 50 мс:

| Участок внутри этой паузы | мс |
| --- | ---: |
| DM-пакет эффектов, включая завершение callback | 211,1 |
| Публикация состояния | 131,3 |
| Получение пакета команд | 3,8 |
| Ожидание готовности worker | 2,3 |
| Интервал сна MC вне вложенных операций | 40,3 |
| Остальное/непрослеженное | 1,8 |
| Вся пауза | 390,6 |

Публикация и эффекты занимают 87,7% этой паузы. Это wall-time интервалы,
а не отдельное измерение CPU каждого вызова. Родительские и дочерние
интервалы не суммировались дважды.

| Максимальная длительность отдельного вызова в трассе | мс |
| --- | ---: |
| Rust: пакет эффектов | 217,3 |
| Rust: публикация | 153,1 |
| Rust: подготовка входных данных | 74,8 |
| Rust: ожидание worker | 12,5 |
| DM: порция активных тайлов | 47,5 |
| DM: порция ветра | 46,2 |

За всё Rust-окно блокирующее ожидание worker заняло 196,9 мс.
Дополнительный пропуск MC из-за starting_tick_usage > 70 был один;
соответствующий интервал ожидания — 64,1 мс, причём он может включать
вложенную работу. Гипотеза, что дополнительный backoff MC является
основной причиной среднего ТД, не подтвердилась.

В десятиигровом окне максимального ТД публикация занимает 2,562 с,
эффекты 3,553 с, подготовка входов 1,229 с, ожидание worker — 0,038 с.
Средний CPU ниже, потому что общей работы меньше; длительные атомарные
участки всё равно задерживают завершение отдельных игровых тиков.

## Подтверждающие пути кода

- `code/controllers/subsystem/air.dm:458`: исходный цикл активных тайлов,
  проверка бюджета после `process_cell`.
- `code/controllers/subsystem/air.dm:449`: цикл ветра с такой же проверкой.
- `code/controllers/subsystem/air.dm:201`: запуск `run_tick` через
  `INVOKE_ASYNC`.
- `modular_bandastation/atmos_rust/code/world.dm:290`: подготовка входов,
  await, затем продолжение `synchronize_calculation` / `finish_publication`.
- `world.dm:346`: `synchronize_calculation` сразу вызывает `project_changes`.
- `world.dm:397`: `apply_frame` подряд публикует изменения и запускает
  `run_callback(executor)`.
- `world.dm:668`: весь список команд обрабатывается одним `on_run`.
- `modular_bandastation/atmos_rust/code/phase.dm:208`: изменения рабочих
  смесей фиксируются на границе всего callback. Эта граница важна при ошибке.

## Предлагаемое исправление

Первый шаг — возобновляемые стадии готового кадра внутри штатного `SSair.fire`:

1. Worker завершает численный расчёт и отмечает кадр готовым. Обычное
   продолжение await не выполняет всю обработку мира самостоятельно.
2. MC запускает полную публикацию газа, живых ссылок и текущих callbacks
   в прежнем порядке. Паузы внутри неё пока нет.
3. На завершённой границе публикации проверяется бюджет. Если он исчерпан,
   `SSair` сохраняет стадию и возвращает управление MC.
4. Следующее штатное продолжение выполняет исходный пакет эффектов
   целиком, с прежним `finish_callback` и прежней обработкой исключений.
5. После его завершения снова проверяется бюджет, затем подготавливаются
   входы и запускается следующий расчёт. Снимок входов не растягивается
   паузой между чтением полей и запуском расчёта.

Это разрывает накопление публикации и эффектов в одной паузе, не меняя
формулы и порядок газообмена и не разделяя газовую транзакцию. Синхронное
обращение к воздуху сохраняет нынешний способ получения свежего газа;
оно должно уметь завершить необходимую публикацию вне обычного расписания.
Следующий расчёт ждёт только обратную связь, от которой зависят его
входные данные. Независимый хвост доставки предыдущего кадра не должен
становиться дополнительным барьером для worker.
Готовность worker не должна отдельно переключать published-снимок,
оставляя выданные DM-ссылки на предыдущем кадре: численная публикация
и обновление ссылок остаются одной непрерываемой операцией. Продолжение
нужно запускать в ближайшем доступном бюджете MC, а не ждать очередной
интервал `SSair.wait`; новый механизм не должен удваивать times_fired
или искусственно менять частоту физических расчётов.

Важное ограничение: перенос в MC сам по себе не укоротит отдельную
публикацию 153 мс или пакет 217 мс. Поэтому гарантировать паузы уровня
DM нельзя. После первого A/B следующий безопасный шаг — перенести
служебный обход команд и чтение контекста в C API/Rust, сохранив вызовы
игровых DM-procs в том же порядке. Это уменьшает непрерывный участок
без изменения границы фиксации газа.

### Обязательное перекрытие работы

Уточнение пользователя: перенос стадий в MC не должен превращать систему
в последовательное выполнение математики и всей доставки. Целевой конвейер:

`обратная связь N → окончательный снимок входов N+1 → worker N+1`,
а независимая доставка N выполняется параллельно последнему этапу.

В текущем коде такого перекрытия соседних атмосферных расчётов ещё нет:
`run_tick` запрещает старт при worker_cycle/processing, а `Store::begin_at`
проверяет EffectsPending. Сейчас worker перекрывается с другими игровыми
подсистемами, но не запускает следующий кадр поверх обработки предыдущего.

Разделять работу нужно по фактическим зависимостям:

- Чтение/запись DM-объектов через C API и вызовы игровых procs выполняются
  на основном потоке. Фоновым может быть численный расчёт и подготовка
  независимых буферов/описателей без доступа к BYOND.
- Эффект, добавляющий газ, меняющий температуру, блокировку или геометрию,
  должен войти в окончательный снимок следующего расчёта. Иначе, например,
  добавленный предметом CO2 попадёт в химию на шаг позже нынешнего поведения.
- Текущая публикация содержит callbacks оверлеев и жизненного цикла очагов.
  Считать всю её визуальную часть безопасной без проверки нельзя. Для
  конвейера сначала выделяется доказанно независимый хвост; неизвестные
  обработчики остаются на совместимом пути.
- Снимки и пакеты имеют номер кадра и версию привязки. Доставка N не
  должна затереть уже рассчитанный N+1; ошибки и синхронные обращения к
  воздуху сохраняют прежний порядок. Дополнительные удерживаемые снимки
  и COW-копирование учитываются в памяти 32-битного процесса.

Спекулятивный расчёт N+1 до завершения обратной связи N — отдельный
вариант с обнаружением конфликтов и пересчётом. Его нельзя включать одним
снятием защиты: нужна проверка как газовых записей, так и топологии.

Критерий проверки — видимое на временной трассе перекрытие разрешённых
операций, без ожидания независимой доставки. Снижение среднего ТД/p99
проверяется отдельно: занятый worker сам по себе не устраняет длинный
непрерывный участок на основном потоке. Этот конвейер пока не реализован.

Полное деление большого пакета по тайлам — более сильный вариант, но
оно затрагивает ранее выбранную атомарность газомодифицирующих эффектов
при поздней ошибке. Такое изменение нельзя включать как незаметную
оптимизацию. Ранее опробованные порции отдельных безопасных эффектов
не равны предлагаемому разделению завершённых стадий готового кадра.

## Проверенная граница конвейера

Проверка `next_calculation_must_include_previous_effect_feedback_before_archiving`
в `rust/atmos/src/phase_tests.rs` воспроизводит два порядка на действующем
численном ядре, без изменения рабочего планировщика. Два соседних тайла
содержат по 100 молей азота; эффект предыдущего кадра добавляет первому
ещё 100 молей перед следующим расчётом.

| Порядок | Архив первого тайла | Газ после шага: первый / второй тайл |
| --- | ---: | ---: |
| Эффект, затем начало расчёта | 200 | 150 / 150 |
| Начало расчёта, затем запись эффекта | 100 | 200 / 100 |

Это не обнаруженная ошибка текущего worker: текущий барьер как раз
сохраняет первый порядок. Тест показывает, почему нельзя убрать барьер
ради перекрытия. Журнал внешних записей сохраняет массу газа, но применяет
запись после численного шага; распространение добавленного газа сдвигается
на следующий шаг. Это крупное различие, а не округление f32.

Публикацию также нельзя целиком объявить независимой: `sync_hotspot`
создаёт объект через `/obj/effect/hotspot/Initialize`, который вызывает
`air_update_turf(FALSE, FALSE)`. Публикация меняет входное состояние
следующего шага. Существующий игровой тест
`native_projection_callback_order_*` отдельно защищает возможность
обработчика оверлея наблюдать и менять сохранённую смесь следующего тайла.
Следовательно, изменение очередности обновления всех смесей и callbacks
тоже требует сохранения совместимого пути.

Полностью независимую численную подготовку пакетов можно переносить
в worker. Запуск следующей физики до завершения обратной связи требует
либо проверки входов с отбрасыванием/пересчётом спекулятивного результата,
либо явного изменения игрового порядка. Первый путь может увеличить CPU
и память, второй меняет поведение. Выбор запрошен у пользователя;
рабочий конвейер пока не изменён.

Пользователь разрешил задержку обратной связи на один расчёт. Следующая
проверка `late_full_mixture_commit_overwrites_transport_instead_of_replaying_feedback`
выявила отдельное ограничение: `commit_air` передаёт `Write::Commit`, то есть
полные моли и температуру. При 100 молях на первом тайле и 0 на втором
расчёт переносит соседу 50 молей. Если эффект, работавший со старой смесью,
добавляет 10 и затем фиксирует полные 110, после расчёта получается
110 + 50 = 160 молей вместо ожидаемых 110. Обе численные проверки прошли.
Это также не ошибка текущего защищённого пути, а подтверждённая
несовместимость простого применения полной старой смеси при перекрытии.

Предложены ожидание свежей смеси при её выдаче, разностные записи с
отдельными правилами конфликтов или отмена/пересчёт. До выбора рабочего
способа барьеры не изменены. Разрешение задержки обратной связи само
по себе не разрешает потерю/создание газа.

Весь набор Rust-тестов прошёл: 109/109; `cargo fmt --check` также прошёл.
Это проверка численного контракта Rust, не новый запуск
DreamDaemon. Сравнение производительности нового конвейера с DM и текущим
Rust ещё не выполнялось, поскольку сам конвейер не реализован.

## Проверки перед включением

- Сохранённые ссылки и списки смесей свежи после публикации; callback
  первого тайла по-прежнему может менять следующий тайл в прежнем порядке.
- Замена пола, удаление владельца и binding_version повторно проверяются
  после каждой новой границы продолжения; старые эффекты не повторяются.
- Поздняя ошибка эффекта имеет ту же границу фиксации/отбрасывания газа,
  worker восстанавливается, незавершённые стадии не проигрываются дважды.
- Синхронные remove_air/assume_air, дыхание и доступ к смеси между
  публикацией и эффектами сохраняют порядок уже согласованных фаз.
- Один законченный расчёт учитывается один раз, включая MC pause/resume;
  следующий расчёт не обгоняет эффекты предыдущего.
- Отдельный обычный A/B: средний ТД, p99/max MC, CPU главного потока и
  процесса на расчёт, память, число расчётов. Затем повтор трассы пауз.

## Методика и ограничения

Диагностические копии текущей финальной сборки и чистого DM, MetaStation,
seed 29051994, одинаковые входы плазменного сценария. 30 игровых секунд
прогрева и 60 секунд измерения. Серверы работали по одному; атмосферная
DLL идентична DLL предыдущей итоговой серии. Рабочий код не изменялся.

Синхронные вызовы обрамлены монотонными метками rust-g. Дополнительно
записаны состояния MC и интервалы ожидания. Они относятся к корутинам
основного потока: интервал MC sleep может содержать асинхронное продолжение
атмоса и не равен простою CPU. Вклад выбирается по вложенному интервалу;
сумма проверяется на равенство длительности паузы. Анализатор проверен
на вложенных, пересекающихся и пустых интервалах.

В диагностике средний ТД Rust — 25,27%, DM — 0,06%. Последнее сильно
отличается от обычного DM-контроля 15,24%; диагностические метки и фоновое
тактирование меняют условия. Эти числа не подменяют обычное сравнение
28,19% / 15,24%. Доказательство здесь — расположение и размеры блокирующих
участков плюс подтверждающий код, а не сравнение CPU с включённой трассой.

Оба захвата завершились с нулевым кодом DreamDaemon. В измеряемых окнах
runtime нет; известный runtime трупа Rust-контроля случился за 249 с до окна.
Неизвестные ошибки не разрешались. Исходные данные, SHA, интервалы,
состояния MC и результаты: `PIPE_LATENCY_DIAGNOSIS_RESULTS.json`;
скрипты и копии: `tmp/atmos-pipe-latency/`; сырые захваты:
`tmp/profiling/pipe-latency-{worker,dm}-01/`.

Исправление пока не реализовано и его эффект не измерен. 50+ игроков и
длительный раунд не проверялись; commit/push/PR не выполнялись.
