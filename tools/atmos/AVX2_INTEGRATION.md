# AVX2 в нынешнем хранении 20 газов

Эксперимент в ветке rust-atmos-experiment, 2026-11-04. По решению пользователя
в рабочее ядро перенесена только пакетная арифметика переноса молей. Плотное
хранение 24 слотов из варианта Б не переносится. Арифметика настоящего ядра
ускорилась в микротестах; экономия CPU/RAM всего сервера относительно DM
не подтверждена. Лимит памяти не выполнен. Включение на рабочих серверах
не выполнено. Полные числа, хеши и статусы захватов:
[AVX2_INTEGRATION_RESULTS.json](AVX2_INTEGRATION_RESULTS.json).

## Реализация

`cargo build --release --target i686-pc-windows-msvc --features byond,simd`
собирает кандидат. Без `simd` сохраняется скалярный контроль. Поддержка AVX2
проверяется при выполнении; на другом CPU используется скалярный путь.

`src/simd.rs` читает существующий архив из 20 f32: два пакета по восемь
и последние четыре через SSE. Используются unaligned load/store, чтения
за границей массива нет. Padding, новые поля ячеек, дополнительные heap-массивы
и принудительная привязка к ядрам не добавляются. Ленивые массивы пустых смесей,
совместное хранение одинакового космоса и страницы COW сохраняются.

Векторы вычисляют разность, прежнее округление молей и коэффициент отправителя.
Деление не заменено приближённым reciprocal; FMA и горизонтальные суммы
не добавлены. Применение переносов, накопление тепла и молей сохраняют прежний
порядок ключей. Порядок тайлов/связей, реакции, трубы и BYOND ABI 11 не меняются.

Первый кандидат вычислял все 20 слотов даже для двух газов и замедлил такой
микротест на 22%. Итоговый кандидат выбирает SIMD только после объединения
ключей, когда присутствует больше двух газов. Это выбор способа арифметики,
а не отсечение малых количеств газа или изменение физики.

## Корректность

`tmp/atmos-simd/current20-02/report.json`: исходные DM-процедуры против AoS,
пакованного SIMD, SoA и настоящего `Sample.share()` из DLL-ядра. Пройдено
258 сценариев, в том числе 10000 шагов с регулярной подпиткой смеси.
Все четыре Rust-потока состояния побитово совпали:
`c3b9ffdd790746676059e0ba446cd7773a7df148d643b255afba182196c7bc38`.

С BYOND моли, температуры, архивы и ключи совпадают точно. Ранее согласованный
допуск касается только возвращаемого перепада давления: до 0.1 kPa при том же
знаке и null. Максимум в этом наборе — 0.0546625 kPa при 96562.7656 kPa.
Новых игровых допусков ради SIMD не вводилось.

Оба итоговых набора features прошли 84 Rust-теста. Дополнительно проверяются
побитовые переносы, округление, последние четыре слота, нулевые коэффициенты
и отсутствие материализации массивов при обмене пустых смесей.

Игровой harness прошёл для scalar и итогового AVX2: 12 сценариев,
49 графов / 980 тиков, проверки привязки пола, предметов, оборудования,
worker и восстановления после ошибки эффекта. Итоговый AVX2-захват:
`tmp/atmos-phase/integration-avx2-03/report.json`, ошибок и расхождений нет.
Первый отклонённый прогон сохранён: исходная ошибка рыбьего хвоста при
Atoms.Initialize, до включения native backend; она не исправлялась.

## Микробенчмарк настоящего ядра

Windows i686, Intel i7-10700F (8C/16T), Rust 1.86.0, Criterion 0.5.1.
Привязки потоков к ядрам нет. Снимки исходников и бинарников:
`tmp/atmos-avx2-builds-02/{scalar,avx2}/manifest.json`. Второй последовательный
запуск поменял порядок вариантов: сначала AVX2, затем scalar. По 20 выборок,
1 s прогрева и 3 s целевого измерения; память смесей и архивы создаются
вне измеряемого участка. В таблице среднее время пакета обменов N-1 соседств.

| Смесей / газов / теплообмен | Scalar | AVX2 с порогом | Scalar / AVX2 |
| --- | ---: | ---: | ---: |
| 64 / 2 / нет | 4.836 us | 4.416 us | 1.10x |
| 4096 / 4 / нет | 0.445 ms | 0.384 ms | 1.16x |
| 4096 / 4 / есть | 1.855 ms | 1.631 ms | 1.14x |
| 4096 / 20 / есть | 3.187 ms | 2.497 ms | 1.28x |
| 65025 / 4 / есть | 32.393 ms | 29.936 ms | 1.08x |
| 65025 / 20 / есть | 55.054 ms | 36.606 ms | 1.50x |

На двух газах работает скалярная арифметика: небольшую разницу времени нельзя
приписывать SIMD. Большие смеси показывают выигрыш; цель 15x не достигнута.
Этот тест не включает реакции, группы, топологию, COW и обмен с DM. Результаты
не означают такое же ускорение атмоса или всего сервера. L1/L2 misses не измерены.

## Сопоставление с Paradise

Зафиксированная версия Paradise:
`5aca8afbcf00ef1f2bb96e179bf1389289551689`. В [GasSet][model] хранится
обычный массив `[f32; GAS_COUNT]`; моли и теплоёмкость кэшируются с dirty-флагом.
В [решателе][flow] используются циклы по газам и другая численная модель.
Эти два файла проверены непосредственно; готовая ручная AVX2-реализация
в них не обнаружена. Копирование их формул не сохраняет физику Banda.

Поэтому сохраняется полезная граница MILLA: игровые объекты в DM, численное
состояние и расчёт в Rust, безопасные фазы и запись только изменённых смесей.
AVX2 здесь — локальный эксперимент над совместимым Banda-расчётом, а не
заявление о SIMD-устройстве или производительности Paradise. Запуска Paradise нет.

## Измерение всего процесса

Одни и те же MetaStation, BYOND 516.1688, seed 29051994, общий harness и
runtime DLL; без клиентов. Отдельные последовательные запуски исходного DM,
scalar worker и AVX2 worker для покоя, локального пожара, плазменного
наводнения станционного z и взрыва СМ. Профилировщик включён одинаково.

Новый `atmos-flood` заполняет все подходящие открытые полы станционного z
в пределах карты 255x255. Стены и космос не заменяются полом: фактическое
число и координаты смесей берутся из metadata, это не 65025 открытых тайлов.

Диагностическая feature `worker-profile` добавляет счётчики завершённых
численных задач, CPU-времени и Windows thread cycles. Интервал заканчивается
после staging, до Byond_Return; запуск/завершение потока и DM-эффекты сюда
не входят. Windows thread CPU может округляться грубо для коротких задач;
сырые million cycles приводятся отдельно, без пересчёта по номинальным GHz.
Задача на границе окна может целиком попасть в один из соседних интервалов.

CPU всего процесса и главного потока дополнительно измеряются ОС. Разность
содержит все остальные потоки; она не объявляется точным CPU worker.
Сравниваются CPU-секунды на одинаковое игровое окно, число завершённых тиков
и затраты всего сервера на тик. Память — private в окне и наблюдаемый OS peak
commit/working set с инициализацией; эти величины не складываются.
Пик ОС сохраняет короткие всплески между опросами, но последний участок
перед завершением процесса может не попасть в чтение счётчика.

Runtime отклоняет захват. Известные исходные ошибки не исправляются и
не становятся основанием объявить ошибочный прогон успешным замером.

## Чистые прогоны DreamDaemon: покой и локальный пожар

Окно — 60 игровых секунд. CPU% — доля одного логического ядра, не всей машины.
CPU-секунды полного окна оценены по OS samples внутри него; это затраты
всего сервера. Числа на тик не являются изолированной стоимостью атмоса.
Поле `over` встроенного профиля означает overtime после исчерпания бюджета
тика и входит в self; оно не является накладными расходами профайлера и
не прибавляется к total. [Пояснение автора BYOND][profile-times]. Влияние самого
профайлера отдельно не оценивалось; во всех режимах он включён одинаково.

| Сценарий / режим | CPU всего / главный / остальные, % | CPU-s всего за окно | Завершённых тиков | CPU-ms всего на тик |
| --- | ---: | ---: | ---: | ---: |
| Покой / DM | 17.30 / 17.30 / 0.00 | 10.40 | 120 | 86.6 |
| Покой / scalar worker | 17.19 / 17.03 / 0.16 | 10.32 | 120 | 86.0 |
| Покой / AVX2 worker | 16.67 / 16.57 / 0.11 | 10.02 | 120 | 83.5 |
| Пожар / DM | 29.75 / 29.75 / 0.00 | 18.41 | 119 | 154.7 |
| Пожар / scalar worker | 34.68 / 33.71 / 0.97 | 21.06 | 119 | 176.9 |
| Пожар / AVX2 worker | 31.65 / 31.28 / 0.37 | 19.16 | 120 | 159.6 |

Работа численного worker отдельно, до уведомления BYOND:

| Сценарий / режим | Jobs | CPU-s worker* | Million thread cycles |
| --- | ---: | ---: | ---: |
| Покой / scalar | 120 | 0.078125 | 103.263 |
| Покой / AVX2 | 120 | 0.062500 | 130.476 |
| Пожар / scalar | 119 | 0.593750 | 1113.867 |
| Пожар / AVX2 | 120 | 0.218750 | 1126.929 |

* Для коротких новых потоков Windows CPU-счётчик грубый. Разница 0.59 → 0.22 s
при почти неизменных cycles не доказывает трёхкратного ускорения worker.
Для точного эффекта арифметики используются одинаковые входы Criterion.

В одном пожарном прогоне AVX2 сократил CPU всего сервера на тик относительно
scalar примерно на 9.8%, но остался на 3.2% дороже исходного DM. При этом
конечное число активных тайлов различалось: 712 / 716 / 622 у DM / scalar / AVX2.
Даже при одинаковом seed планирование и фоновые события расходятся; число
трубопроводов в пожарных прогонах совпало (296), но в покое было 343 / 331 / 296.
По одному прогону нельзя приписать весь сдвиг SIMD или подтвердить небольшую
экономию инфраструктуры. Большого выигрыша всего процесса не установлено.

В scalar-пожаре профиль показал 90086 вызовов `sync_air`, 60561 декодирование
DM-смеси, 334212 вызовов `ensure_binding`. `project_changes` занял 4.434 s
включая дочерние вызовы, `sync_air` — 3.431 s. Эти времена пересекаются;
они не складываются и не прибавляются к OS CPU. Они указывают на мост
и публикацию DM-состояния как оставшийся существенный расход. AVX2 его
не устраняет. У исходного DM `share` имел self 0.034 s в покое и 1.603 s
при пожаре из 10.625 / 18.916 s self профилируемых процедур соответственно.

| Сценарий / режим | Private в окне, max MiB | OS peak commit с загрузкой, MiB |
| --- | ---: | ---: |
| Покой / DM | 1684.6 | 1958.9 |
| Покой / scalar | 2147.7 | 2160.2 |
| Покой / AVX2 | 1839.3 | 2116.6 |
| Пожар / DM | 1674.8 | 1941.7 |
| Пожар / scalar | 1823.2 | 2076.7 |
| Пожар / AVX2 | 1824.1 | 2082.7 |

Память в пожаре у двух Rust-вариантов практически одинакова. Разница 308 MiB
между их прогонами покоя не объясняется SIMD: форматы ячеек и смесей одинаковы,
механизм её появления этим экспериментом не установлен. Прежний высокий
расход процесса воспроизвёлся у scalar. Экономия памяти относительно DM
не подтверждена. Лимит <2 GB не выполнен; пик Rust выше даже 2 GiB.

Исходные захваты: `tmp/profiling/avx2-01-empty-station-{dm,scalar,avx2}`,
`avx2-02-atmos-fire-dm`, `avx2-01-atmos-fire-{scalar,avx2}`. Строгие парные
сравнения: `tmp/atmos-avx2-profiles-01/{idle,fire}-comparison.md` и JSON.
Первый `avx2-01-atmos-fire-dm` отклонён из-за исходной ошибки рыбьего хвоста
в Atoms.Initialize, до измеряемого окна; повтор сохранён отдельным каталогом.

## Наводнение уровня: диагностика, не принятый бенчмарк

Во всех трёх прогонах лог содержит 51 сообщение о повторном повреждении
разрушенных рам картин (`atom_defense.dm:23`, `fire_act` / burning). Ошибка
воспроизведена на исходном DM до запуска Rust-вариантов; предметы не исправлялись.
Все три захвата отклонены строгой проверкой runtime, в таблицу выигрыша не входят.
Количество начальных полов также различалось: 12283 / 12285 / 12286
у DM / scalar / AVX2. Это дополнительная причина не считать их парным тестом.
Разница — (76,174), (133,173), дополнительно (66,105) у AVX2. На всех этих
координатах карта содержит `airlock/abandoned`: helper в
`code/modules/mapping/mapping_helpers.dm:261` случайно может заменить шлюз
стеной. Это вероятное объяснение разной геометрии, а не подтверждённая
несовместимость адаптера. Начальные типы этих тайлов в захватах не записывались.

В диагностическом scalar-захвате 60 игровых секунд заняли 214.294 реальных,
в AVX2 — 214.969. Это наблюдение ошибочных запусков, не доказательство
замедления относительно DM или измерение чистого эффекта инструкций.
Профиль scalar выявил 1053398 вызовов `sync_air`, 1005828 декодирований смеси,
1066056 обновлений визуала. `project_changes` с дочерними вызовами занял
101.667 s, `sync_air` — 89.195 s; эти пересекающиеся времена не складываются.
Между OS samples основному потоку приписано 186.172 CPU-s, остальным — 7.188 s.
Это прямое свидетельство больших расходов публикации состояния в DM под
массовой нагрузкой, несмотря на маленькую долю собственно численного worker.

Jobs worker составили 80 / 75, а полностью завершённые native-фазы — 13 / 4
у scalar / AVX2. Из-за ошибок эффектов эти счётчики означают разную работу;
делить CPU на успешные фазы и объявлять полученное стоимостью расчёта нельзя.
Native heap отдельно в этом этапе не профилировался. Артефакты:
`tmp/profiling/avx2-01-atmos-flood-{dm,scalar,avx2}`.

## СМ на плазме: диагностика, не принятый бенчмарк

Все три прогона завершили взрыв; СМ удалена. Начальные параметры incident
побитно/структурно одинаковы: центр (169,154,2), 33 тайла камеры, по 300 mol
plasma при 1200 K, internal_energy=5000, explosive, радиус 35.
У обоих Rust-вариантов в конце нет ожидающего worker, численные задачи
продолжают завершаться после взрыва. Новых ошибок привязки пола не обнаружено.

Исходный DM получил ошибку `removeStaticPower` голодека (`areas.dm:561`)
и семь ошибок обращения к таймерам отсутствующей excited group. Последний
случай относится к ранее согласованному пропуску таймеров отсутствующей группы
в экспериментальном backend; исходная DM-база осталась нетронутой.
Scalar и AVX2 получили по одной той же ошибке питания голодека при разрушении
настенной камеры. Она воспроизведена без Rust. Предметы/питание не исправлялись.

Все СМ-захваты отклонены проверкой runtime. Их CPU нельзя выдавать за
успешное сравнение нагрузки; первичные метрики сохранены в JSON с accepted=false.
Артефакты: `tmp/profiling/avx2-01-sm-plasma-{dm,scalar,avx2}`.

## Проверки и повторение

Проверены 84 Rust-теста в release/i686 для обоих наборов features; `cargo fmt
--check`; `clippy --all-features --lib --examples -- -D warnings`; `clippy
--features simd --benches -- -D warnings`; Python compile и `git diff --check`.
При объединённом `clippy --all-features --lib --benches` остаются три прежних
замечания items_after_test_module в byond_packets/byond_worker/byond_world.
С отключением только этого lint остальных замечаний нет. Расположение старых
тестовых модулей ради эксперимента не менялось.

Все текущие Rust-исходники и Cargo-файлы сверены с хешами frozen builds-02.
Рабочая DLL прежнего этапа осталась с SHA256
`850d53aec04a9a2dfd489605bd02d2e91d926206c663ab3ac63639c94481d49d`.
Захватов 13: шесть приняты, семь отклонены, включая первый DM-пожар до повтора.
Коммит и push этого этапа не выполнялись.

```powershell
cargo bench --manifest-path rust/atmos/Cargo.toml --target-dir tmp/atmos-new-target --target i686-pc-windows-msvc --features simd --bench atmos_bench --no-run --locked
python tools/atmos/simd_bench.py --byond E:/Games/BYOND/bin --name <unique-name> --binary <compiled-atmos_bench.exe>
$env:CRITERION_HOME = '<new-capture-directory>/criterion'
& '<compiled-atmos_bench.exe>' --bench production_share
python tools/profiling/run.py --byond E:/Games/BYOND/bin --name <unique-name> --scenario atmos-fire --rust-dll <frozen-dll> --threaded
```

Для scalar build исключается feature simd. Диагностические DLL обоих режимов
добавляют worker-profile. Скрипт run.py при отсутствии --compiled-binary
компилирует актуальный DM harness; замеры выполняются последовательно.
Новый target-dir обязателен для сохранения прежних бинарников эксперимента.

Не проверены 50+ игроков, Linux, длительный раунд и L1/L2 misses.
Риск: локальный выигрыш арифметики может быть незаметен на фоне DM и остальных
стадий атмоса; соблюдение лимита памяти всего процесса проверяется отдельно.
