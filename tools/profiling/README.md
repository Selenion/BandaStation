# Исходный профиль сервера

Сначала замеряем текущий DM-код. После оптимизации повторяем тот же сценарий
на том же компьютере с той же версией BYOND, картой, настройками и профайлером.
Каталог реакций и эксперимент Rust остаются в `tools/atmos` и `rust/atmos`.

После проверки работоспособности общего подключения Rust сравниваем DM и Rust
в трёх обязательных сценариях: покой без активных реакций, возгорание
(`atmos-fire`) и взрыв суперматерии на плазме. Для каждого сохраняем CPU,
working set/private memory, длительность обработки атмоса и число обработанных
тиков. Для взрыва отдельно учитываем подготовку, сам взрыв и восстановление.
Условия обеих реализаций одинаковы: компьютер, BYOND, карта, конфигурация,
начальные газы/энергия СМ, окно сбора и настройки профайлера. Нужны повторные
прогоны и разброс результатов; имеющиеся исходные профили не заменяют парные
замеры. Приняты первые пары покоя и поджога; они пока хуже исходного DM.
Исторические захваты взрыва СМ отклонялись из-за runtime-ошибок. Числа,
артефакты и ограничения — в [отчёте оптимизации](../atmos/OPTIMIZATION.md).
Основная DM-база должна использовать исходный код без накладных расходов нового
адаптера. Режим текущей ветки с выключенной DLL проверяется отдельно, чтобы
служебные перехваты сами не завышали исходную стоимость DM.

Профилирование уже встроено в сервер:

- `SSprofiler` пишет JSON с процедурами и SendMaps;
- MC показывает стоимость подсистем и разбиение затрат `SSair`;
- `-params tracy=1` подключает `prof.dll`/`libprof.so`, без правок игрового кода.

Для исходного автоматического замера:

```powershell
$env:DM_EXE = 'E:/Games/BYOND/bin/dm.exe'
tools/build/build.bat dm
python tools/profiling/run.py --byond E:/Games/BYOND/bin --map metastation --name baseline-01
python tools/profiling/summarize.py tmp/profiling/baseline-01
```

`run.py` создаёт отдельный `local-profile.test.dme` с диагностическим включением,
компилирует его и поднимает локальную копию сервера в `tmp/profiling/<name>`.
Ресурсы доступны через hard links; конфигурация и данные копируются отдельно.
SQL выключен, сетевой адрес — localhost. Рабочие конфиги не изменяются.

Сценарий `empty-station`: старт раунда без клиентов, 30 секунд прогрева и
60 игровых секунд сбора. Сохраняются сырые профили, стоимость подсистем,
счётчики атмосферики, карта, версия BYOND, commit и hash бинарника.
В Windows также раз в секунду снимаются CPU, working set и private memory
именно запущенного процесса. В итоговую сводку попадают только отсчёты окна сбора.
Для сравнения worker отдельно снимается CPU исходного потока DreamDaemon,
определённого по самому раннему времени создания. TID фиксируется на запуск;
при недоступном счётчике поле отсутствует и вывод о CPU главного потока запрещён.
Используются [GetThreadTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getthreadtimes)
и read-only snapshot потоков, affinity/priority не меняются. Контрольный сценарий
`tmp/thread-cpu-probe.py`: 0.2 CPU-секунды в главном потоке, затем 0.2 в worker;
счётчик главного потока должен вырасти только в первой части. Проверка прошла:
0.203125 / 0.0 CPU-секунды главного потока и 0.203125 CPU-секунды процесса
во время worker (сырые результаты: `tmp/thread-cpu-probe.json`).

Фоновый Rust включается в изолированном запуске дополнительным `--threaded`
вместе с `--rust-dll`. Параметр записывается в manifest и метаданные;
harness проверяет фактически включённый режим. Синхронный Rust, worker и
исходный DM измеряются последовательно, без других тестовых серверов в окне.
Средняя стоимость подсистемы в MC — сглаженная оценка, не сумма CPU за окно.
Новые парные прогоны используют фиксированный seed 29051994 и выключенные
station traits. Это не делает последующие события/планирование идентичными:
число активных тайлов и очагов в начале/конце записывается отдельно.

Сценарий `--scenario atmos-fire` после прогрева заполняет 64 проходимых тайла
пола в координатном порядке x=100..150, y=100..150 на первом станционном z:
100 mol O2, 300 mol N2, 20 mol plasma, 700 K. Включает эти тайлы в SSair.
Координаты фактически затронутых тайлов записываются в метаданные. Газ однократно
задаётся перед окном сбора; далее идёт обычная игровая симуляция без вмешательств.
Это воспроизводимый по исходным газам локальный инцидент, не модель 50 игроков.

`--scenario atmos-flood` использует тот же состав и температуру, но заполняет
все подходящие открытые полы станционного z в пределах 255x255. Стены и космос
сохраняются; metadata содержит фактические координаты. Это нагрузка целого
уровня, но не искусственные 65025 открытых тайлов.

Для сравнения SIMD можно собрать контроль с `--features byond,worker-profile`
и кандидат с `--features byond,worker-profile,simd`, сохранив DLL раздельно.
Необязательный opcode 39 диагностической сборки возвращает CPU и million
cycles завершённых численных задач. Счётчик заканчивается после staging,
до Byond_Return; стоимость DM-эффектов и жизненного цикла потока не включена.
Задачи могут пересекать границу окна, Windows CPU-время коротких задач
округляется грубо. Cycles не переводят в секунды по номинальным GHz.
Обычная сборка этих счётчиков не имеет. Подробности:
[AVX2_INTEGRATION.md](../atmos/AVX2_INTEGRATION.md).

Отсчёты ОС дополнительно сохраняют peak working set и peak commit всего
процесса с инициализацией. Пик ОС удерживает всплески между опросами; последний
участок перед завершением может не попасть в чтение. Это отдельные метрики
от private в игровом окне. Лимиты 2 GB (2000000000 B) и 2 GiB (2147483648 B)
не взаимозаменяемы; память working set и commit не складывается.

`--scenario sm-plasma`: камера существующего главного кристалла заполняется
300 mol чистой plasma на каждый открытый пол, 1200 K. Сам кристалл получает
internal_energy=5000; штатный `calculate_gases()` вычисляет газовые коэффициенты.
После начала окна вызывается `force_delam()` со штатной стратегией explosive:
реальные радиация, аномалии, взрыв, разрушение карты и дальнейший атмос.
Обратный отсчёт не измеряется; это тест последствий заданного взрыва, а не
естественного разгона двигателя. Центр, тайлы, радиус и удаление СМ записываются.

Нетронутую базу исходного DM можно подготовить без изменения Git/ветки:

```powershell
python tools/profiling/baseline.py --name original-head-unique
python tools/profiling/run.py --byond E:/Games/BYOND/bin --name dm-idle-unique --source-root tmp/profiling-sources/original-head-unique
python tools/profiling/run.py --byond E:/Games/BYOND/bin --name rust-idle-unique --rust-dll rust/atmos/target/i686-pc-windows-msvc/release/bandastation_atmos.dll
```

`baseline.py` берёт список файлов и изменённые blob из HEAD. Исходники и конфиги
имеют независимые копии, бинарные ресурсы доступны через hard links. Оба варианта
получают одинаковые локальные runtime DLL, их SHA сохраняются. В Rust газ
задаётся через безопасный API; панельные счётчики тоже читаются из Rust.
Для повторов без новой компиляции есть `--compiled-binary <предыдущий>/tgstation.dmb`;
его используют только для той же версии исходников и того же harness SHA.
Прогоны выполняют последовательно; другие тяжёлые процессы не запускают
в измеряемом окне. Пара на сценарий — предварительная оценка, не статистика.

`compare.py --pair <dm-folder> <rust-folder> --output <new-name>.md`
проверяет совпадение версии, карты, seed, настроек и входов инцидента,
сохраняет таблицу и JSON с CPU, private, проходами и реальным временем.
Для нескольких сценариев `--pair` указывается повторно. Неожиданные runtime
за весь запуск запрещают принимать захват; данные не удаляются. Известные
ошибки исходного DM, не относящиеся к переносу атмоса, допускаются по точным
правилам в `runtime_check.py`: текст, процедура, файл и, для общих сообщений,
контекст стека. Номер строки не участвует: он сдвигается при добавлении кода.
Автоматически разрешать все ошибки вне `atmos_rust` или любые ошибки исходного
DM нельзя: вызовы адаптера достигают общего кода, а исходный дефект атмоса
может входить в проверяемое поведение.

На 2026-11-05 подтверждены рамки картин, граната с нулевой прочностью,
отсутствующая позиция при деморализации взрывом СМ и каналы питания голодека.
Свежие DM-контроли также подтвердили `throw_at` удаляемого органа при создании
трупа и `pre_impact`/`throw_impact` булавки хвоста с отсутствующей целью.
Эти правила требуют соответственно контекста corpse organ_loss и точного
типа предмета; ошибки метания других предметов не разрешаются.
Для каждого правила указан сохранённый контроль без Rust. Водяной бак,
`null.volume` и ошибки excited group в исключения не входят. Общая ошибка
без необходимого стека считается неожиданной. Бесконечные циклы, ненулевой
код завершения DreamDaemon, таймаут и отсутствие завершённого профиля по-прежнему
не позволяют принять запуск.

`runtime-validation.json` и manifest содержат `clean`,
`accepted_with_known_runtimes` либо `failed`, сигнатуры, подтверждения,
счётчики и пути логов. Счётчик берёт максимум для одной сигнатуры по логам:
копии событий в DreamDaemon, JSON и Logis не суммируются. `compare.py`
переносит эти сведения в JSON и явно перечисляет известные runtime в Markdown.
Их наличие не делает запуск неуспешным, но разница частоты ошибок и объёма
прерванной работы остаётся ограничением выводов о быстродействии.

Сравнение требует записанного run.py подтверждения успешного захвата,
одинаковых hash стенда и общих runtime DLL. Прежние результаты и manifests
автоматически не переписываются новой политикой. Проверка сохранённых логов
без запуска сервера: `validate_runtime_logs(Path(...))` из `runtime_check`.
Тесты: `python -m unittest discover -s tools/profiling -p test_runtime_check.py -v`.

Итоговая серия с AVX2 и worker: [FINAL_COMBINED.md](../atmos/FINAL_COMBINED.md).
Два завершённых DM-замера приняты после проверки новых точных сигнатур;
исходные отказы сохранены, основания принятия записаны отдельно в
`reviewed-manifest.json`. Это явно оформленный пересмотр в итоговом отчёте,
а не автоматическое переписывание старых manifest или выбор повторного прогона.

Вторая таблица compare.py показывает завершённые расчёты за реальную секунду,
оценку CPU-секунд за игровое окно и CPU всего сервера на тик атмоса. Оценка
CPU полного окна: средний CPU% между отсчётами × реальная длительность / 100;
отсчёты ОС раз в секунду не совпадают с границами окна. Значение на тик не
изолирует атмосферу от других подсистем и не измеряет задержку одного расчёта.
Главный поток измерен отдельно; разность CPU процесса и главного потока
содержит все остальные потоки, включая worker, а не только его.

Пустая станция полезна для сравнения постоянных затрат, но не представляет сервер
с 50+ игроками. Для окончательного решения нужны отдельные прогоны с активными
мобами, работающим производством/энергетикой, пожаром/разгерметизацией и профиль
живого раунда. SendMaps без клиентов практически не измеряется. Профилировщик
сам добавляет нагрузку: сравнивать прогоны нужно с одинаковыми настройками.

Tracy: https://github.com/spacestation13/byond-tracy. Этот форк заявляет поддержку
516.1685 и 516.1688. Для захвата нужны `prof.dll` соответствующего релиза и
совместимый Tracy server/capture. Перед `-params tracy=1` запустите получатель:
наш `Tracy.enable()` передаёт `init("block")`, и запуск может ждать подключения.
Результаты native profiler и Tracy следует снимать отдельными прогонами.
